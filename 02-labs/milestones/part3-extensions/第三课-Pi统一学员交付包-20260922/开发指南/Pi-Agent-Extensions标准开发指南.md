# Pi Agent Extensions 标准开发指南

> 文档性质：自研开发方法与交付约定，“标准”不是 Pi 官方认证或兼容性承诺。已完成主控源码核查；文中最小命令与清单组合在 Pi 0.85.1 隔离环境完成了 npm 打包、解压换目录、自动加载和 RPC 命令通知验证，入口缺失反例也已验证。尚未完成独立审查、新助手依据指南开发未见需求、TUI 实操及跨版本/平台验证；不能把最小示例的结果外推到全部能力。

本指南用于把自己的需求转化为可实现、可验证、可维护的 Pi Extension。可以直接交给 Claude Code、Codex 或其他编程助手，连同需求与目标项目一起使用。它不绑定工单、特定模型、操作系统或某一种扩展形态。

**正文提供可跨项目复用的判断方法；接口名称、代码与命令以 Pi `v0.85.1` 为参考事实。换版本时仍使用本指南，重新核对实际依赖的接口。**方法的可复用性不代表实现代码能无条件兼容未来版本。

本文负责扩展开发。分发进入同目录的 [Package 标准打包指南](./Pi-Agent-Package标准打包指南.md)。只开发本地扩展时，不必先制作完整 Package。

核验日期：2026-09-21。参考源码为官方 `v0.85.1` 发布提交 `d981de1229ef899957bbe968bc8dcda02a21f477`。本文提供方法与源码依据，文中的教学构造例不是已运行项目的验收记录。

## 1. 从这里开始：给编程助手的使用约定

拿到本文后，先读取目标项目已有说明、代码与测试，再按第 2—7 节完成设计、实现和验证。当前任务已经授权的操作直接推进；只对会改变结果的缺失输入提问，不为每个步骤重复确认。

最低输入是：

| 输入 | 必须弄清楚什么 | 缺失时怎么办 |
|---|---|---|
| 需求 | 谁在什么情况下做什么，完成后能观察到什么变化 | 先形成一个代表任务和明确预期 |
| 目标环境 | Pi 版本、运行入口、Node/二进制、操作系统，是否由 SDK 或 RPC 宿主承载 | 读取实际安装与项目依赖；不能从教程推定 |
| 项目与边界 | 新建还是修改；允许写入的项目；必须保留的行为与数据 | 检查已有代码，锁定最小改动范围 |
| 验收样本 | 正常输入、非法输入、取消/失败输入及预期结果 | 先构造最小样本并标为测试数据 |
| 条件性依赖 | 有无外部服务、凭据、持久化、特殊 UI 或其他扩展 | 只补本需求用到的依赖，不搭空架构 |

只有需求时，可以先完成方案与无外部副作用的最小实现；缺少必要的真实服务或凭据时，标清未验证部分，不伪造服务成功。本文不授权发布包、发送外部消息或操作真实业务数据。

最终交付应让接手者找到：扩展入口、实现文件、配置方式、支持的环境、代表任务、实际验证结果、尚未覆盖的情况。小扩展可以把这些放进一个 README，不要求额外生成多份 Spec 或报告。

## 2. 需求归约：先找到需要改变的行为

### 2.1 用行为描述需求

先写一句：**当什么触发时，读取什么输入，依据什么规则，产生什么输出或副作用，怎样判断完成。**

例如，“做一个漂亮的状态栏”还不是足够的开发输入。可以归约为：“在 TUI 中展示当前上下文占用比例和本会话累计用量；数据未知时显示未知；窗口缩窄后仍能看清主要指标。”这会自然导出数据口径、生命周期和显示测试。

用下面的判断选择最小入口：

| 想改变的行为 | 优先考察 | 必须排除的误判 |
|---|---|---|
| 只改变现有配置或资源内容 | 先核对现有设置与资源机制 | 不因想定制就默认新增 Extension |
| 观察或修改 Pi 的某个运行阶段 | 事件订阅与事件允许的返回值 | 观察事件不一定能拦截或改写 |
| 用户主动执行一个固定动作 | 命令、快捷键、启动参数 | 不必为了调用代码先注册模型工具 |
| 让模型自主调用业务能力 | 自定义工具及其参数、返回合同 | 注册成功不代表模型一定选用 |
| 改变终端的显示或输入体验 | TUI 扩展入口 | 终端组件不是浏览器组件 |
| 接入新模型服务或认证流程 | Provider 扩展接口 | 仅 URL 相似不代表协议兼容 |
| 提供 Web 页面、多用户服务或独立后台进程 | SDK/RPC 宿主应用与 Extension 分工 | 不能把宿主自建能力当作 Pi 原生 Extension API |

一个扩展可以同时用多个入口。**入口、宿主、状态寿命和业务风险是不同维度，不要把它们混成互斥的“扩展类型”。**

### 2.2 使用六个连续决策

| 决策 | 形成的最小产物 | 通过信号 |
|---|---|---|
| 需求归约 | 代表任务、必要能力、不做的事 | 能描述一个正常结果和一个失败结果 |
| 运行映射 | 目标版本、宿主、触发时机、公开 API | 每个必需行为都有可定位入口 |
| 行为契约 | 输入输出、状态、副作用、取消与失败规则 | 不依赖 UI 文案也能判断正确与否 |
| 实现装配 | 最小文件结构与调用关系 | 每个职责有明确位置，没有重复实现 |
| 证据验证 | 样本、预期、实测、证据 | 能区分加载、调用、业务效果与交互成功 |
| 交付演进 | 使用说明、支持范围、打包输入 | 换目录、换版本时知道要核查什么 |

复杂度由需求决定。纯事件观察器无须数据库；一个无状态命令无须恢复状态机；仅支持 TUI 的扩展也不必先开发 Web 前端。

## 3. 运行映射：方法不绑版本，实现必须核对版本

### 3.1 TS 解决加载问题，不解决全部兼容问题

Pi `v0.85.1` 通过 jiti 加载默认导出的扩展工厂，可以直接使用 TypeScript，无须先把每个扩展编译成 JavaScript。但代码仍依赖宿主提供的类型、方法、事件数据、第三方库和运行环境。

已有明确的历史反例：

- `0.83.0` 升级 TypeBox 后移除了若干旧 API，使用这些 API 的扩展需要迁移。
- `0.84.0` 改变了部分 `ModelRegistry` 接口和扩展 OAuth 回调要求；JSON/RPC 的 `message_update` 也去掉了旧累计字段。
- `0.85.1` 修复了 `0.85.0` 意外发布内部实验代码导致的 SDK 导入问题，并明确受支持的本地 SDK、stdio RPC 与源码实验入口的区别。

这些来自固定发布版本的 [官方变更记录](https://github.com/earendil-works/pi/blob/v0.85.1/packages/coding-agent/CHANGELOG.md)。它们证明存在兼容变化，**不证明每次小版本更新都会破坏所有扩展**。不根据文件后缀、版本号或 `peerDependencies: "*"` 推导兼容保证。

### 3.2 为本项目建立最小接口清单

检查对象按五层拆开：

| 层 | 检查内容 | 常见失效信号 |
|---|---|---|
| 加载 | 默认导出、模块格式、依赖解析、公开包导出 | 无法导入、工厂不执行 |
| 接口 | 调用签名、参数、返回结构、事件字段 | 类型错误、调用异常 |
| 行为 | 顺序、取消、错误传播、恢复语义 | 能运行但结果或时序错误 |
| 宿主 | TUI/RPC/SDK 实际提供的交互与生命周期 | 按钮无效、等待不结束、状态串会话 |
| 环境 | Node、系统命令、终端、外部服务与协议 | 作者机器可用，使用者机器不可用 |

在项目 README 或设计记录中列出“用到的 API → 目标版本定义位置 → 最小验证”。只列实际依赖，不抄全 SDK。

核对顺序：实际安装版本及安装包 → 同版本官方文档和公开类型 → 决定性源码 → 官方示例/测试 → 社区实现。源码存在但没有受支持导出、只在实验启动器下可用的能力，不进入默认方案。

升级时先查看版本区间的变更记录，再比较接口清单与实际类型，执行受影响的行为测试。没有变化的业务核心可以复用；变化只在适配层时局部修改。新增核心能力缺失应明确报错或声明不支持；可选显示能力缺失可以降级。不能用 `any`、大范围 `try/catch` 或“检测到函数存在”掩盖语义不兼容。

### 3.3 明确宿主能力

`v0.85.1` 的默认模式如下；自行编写 SDK 宿主时，还需要检查该宿主实际绑定的 UI 与生命周期。

| 模式 | `ctx.mode` | `ctx.hasUI` | 开发约束 |
|---|---|---|---|
| 交互终端 | `tui` | `true` | 可以使用终端组件、浮层和编辑器 |
| stdio RPC | `rpc` | `true` | 支持协议中的对话框/通知；`custom()` 不提供终端组件，返回 `undefined` |
| JSON | `json` | `false` | UI 方法不可作为有效用户交互；stdout 是结构化事件流 |
| Print | `print` | `false` | 不能依赖交互提示完成必需输入 |

因此，`ctx.hasUI` 适合判断通用对话能力，**不足以判断能否渲染 TUI 自定义组件**；后者先检查 `ctx.mode === "tui"`。RPC 客户端还必须实现请求、响应、超时与取消。没有可用确认通道时，需确认的动作拒绝执行或要求显式参数，不能把缺失交互当作同意。

### 3.4 按能力查入口，不背固定 API 百科

以下是 `v0.85.1` 的检索地图；签名以目标版本定义为准。

| 能力面 | 参考入口 | 要核对的合同 |
|---|---|---|
| 生命周期与事件 | `pi.on`；启动、资源、会话、Agent、模型、工具、输入事件 | 发生时机、上下文可用性、可否改写、返回和异常语义 |
| 用户主动操作 | `registerCommand`、`registerShortcut`、`registerFlag`、`getFlag`、命令查询 | 名称冲突、参数与自动补全、命令上下文能力 |
| 模型工具 | `registerTool`、`getAllTools`、`getActiveTools`、`setActiveTools` | 参数校验、工具可见性、动态启用和覆盖合同 |
| 消息和上下文 | `sendMessage`、`sendUserMessage`、`before_agent_start`、`context`、请求事件 | 是否触发下一轮、队列方式、消息顺序、来源与循环 |
| 会话元数据 | `appendEntry`、名称、标签、`sessionManager` | 是否进入模型上下文、分支读取与数据版本 |
| 模型与提供商 | 模型/思考级别控制、`registerProvider`、`unregisterProvider` | 注册与运行时机、认证、刷新、流协议和取消 |
| 动态资源 | `resources_discover` | 发现时机、返回路径、重复发现与生命周期 |
| 终端显示 | `ctx.ui`；消息、Markdown、条目渲染注册 | 目标模式、渲染边界、组件所有权 |
| 外部执行与协作 | `pi.exec`、`pi.events`、Node 服务客户端 | 超时、事件命名、资源释放、进程权限 |

工具注册属于扩展的核心接入面。本文不教授通用 Tool/Skill/Prompt 定义，但不会因此删掉工具、上下文事件或资源发现能力。

## 4. 行为契约：先明确正确行为，再写接线代码

### 4.1 把每个入口写成可检查的合同

| 项目 | 应写清的内容 |
|---|---|
| 触发和输入 | 用户、模型、宿主或外部事件触发；参数、来源、路径基准 |
| 输出 | 给模型的内容、机器可读数据、给用户的显示；哪些只是进度 |
| 状态 | 存放位置、所有者、有效期、更新方式、恢复来源 |
| 副作用 | 读写文件、请求服务、启动进程；目标与允许范围 |
| 失败 | 非法输入、权限不足、超时、取消、依赖不可用分别怎样结束 |
| 并发 | 多次调用能否重叠；是否串行、隔离或检查版本 |
| 验收 | 可观察的输入、结果与反例；如何证明没有错误副作用 |

教学构造例：一个“导出分析结果”能力，在确认前只能生成预览；执行时再次校验目标路径和内容版本；拒绝或超时后文件不存在；成功后返回实际产物路径。重复请求是否复用产物，要按业务请求身份决定，不能把内容相同的合法两次导出强行合并。

### 4.2 事件观察、改写和拦截分别处理

观察事件用于记录事实。改写事件只使用它明确定义的返回结构。拦截事件必须验证拒绝后动作确实未执行。

例如 `input` 可继续、转换或自行处理；`tool_call` 可用于调用前阻止；`tool_result` 修改的是返回结果，不能撤销已经发生的外部写入。不同事件不是同一条可任意拦截的流水线。多扩展注册顺序、短路和合并行为需要按具体事件检查 runner。

在 `v0.85.1` 中，普通扩展事件异常通常记录后继续，`tool_call` 异常会阻止工具，自定义工具执行失败应抛出异常，由宿主转成错误结果。不要以为“监听器抛异常”在所有位置都能实现拒绝策略。

拦截器也不是进程沙箱。Extension 本身执行代码，可以访问 Node 和系统能力；限制模型工具列表，不等于隔离扩展代码。若需求是运行不可信扩展，需要在进程/系统/容器等边界另外实现隔离。

### 4.3 工具的三份输出各负其责

- `content`：给模型使用的结果，避免无限量日志和不必要的大对象。
- `details`：机器读取、状态恢复或界面使用的结构数据，按持久化需求设计版本。
- 自定义渲染：给用户看的调用、进度、最终结果和错误，不改变底层业务事实。

参数 Schema 只能证明形状；文件是否在允许目录内、记录是否存在、用户是否有业务权限仍由执行层判断。工具失败抛错，部分进度不等于成功。传入的取消信号应传播到支持它的 I/O；不支持取消的服务需定义迟到结果处理与补偿，而不是提前显示“已取消”后让写入继续。

覆盖内置工具时，除名称外还要保持依赖方使用的输入、输出、错误和 `details` 合同；默认渲染器可能依赖这些字段。大输出需设定截断规则、保留必要摘要或文件引用，并验证模型真正拿到的内容。不要仅把终端显示折叠后称为减少上下文。

### 4.4 状态按寿命分开

| 状态寿命 | 合适位置 | 恢复/清理原则 |
|---|---|---|
| 单次调用 | 局部变量、调用 ID 对应对象 | 成功、失败、取消都结束；迟到结果不得影响下一次调用 |
| 当前会话/分支 | 扩展实例内缓存＋可重建的会话条目 | 切换、分叉、树导航后从正确分支重建 |
| 跨会话业务数据 | 显式文件、数据库或外部系统 | 定义存储路径、并发、Schema 版本和迁移 |
| 进程共享资源 | 连接、监控器、共享缓存 | 明确谁创建、谁关闭，是否跨会话复用 |
| 界面暂态 | 当前选择、展开状态、草稿 | 与业务事实分离；重绘不重复业务动作 |

不要将模块全局变量等同于会话隔离。Pi 可能复用导入模块，而创建新扩展实例。依赖分支的状态应从当前分支恢复，而非扫描整个会话树，把其他分支的数据混入。

无工具的状态扩展可以使用 `appendEntry` 等公开机制；工具型状态可以利用工具结果 `details`。选择权威存储后，其余只是投影或缓存，不允许两份事实互相覆盖。会话历史的恢复不会自动撤销或重做外部数据库和文件操作。

压缩、恢复、树导航和 `/reload` 分别核查；不要假定一次 `session_start` 重建覆盖所有导航路径。为真实用到的生命周期事件分别设计清缓存、重建和过期任务检查。

`v0.85.1` 会话替换后，旧 `pi`、旧命令上下文和捕获的 `sessionManager` 不应继续用于新会话；需要跨会话交接时，使用替换回调提供的新上下文，只传递仍有效的普通数据。`await ctx.reload()` 返回后仍在旧调用栈，通常紧接 `return`，不要继续使用已清理的扩展状态。

命令具有 `ExtensionCommandContext` 的会话控制能力，例如等待空闲、新建/切换/分叉会话、树导航和重载；普通工具/事件上下文不等同于命令上下文。不要在正在执行的工具内等待其所属 Agent 自己变为空闲，或通过类型断言伪造这些方法。

### 4.5 长任务与资源必须有终点

工厂函数负责注册；异步工厂会阻塞后续启动，必要网络初始化必须有超时。工厂可能在不启动会话的命令中运行，所以不要在其中启动常驻 watcher、socket、计时器或子进程。把这些放到 `session_start` 或真正需要它的命令/工具事件中。

资源有一个明确所有者，关闭操作可重复执行。按实际 API 处理取消信号、事件订阅、计时器和子进程；不能假设每个注册函数都返回 disposer。会话结束、替换、重载及初始化中途失败分别检查；关闭 UI 不代表后台进程已退出。

`ctx.signal` 在没有活动 Agent 轮次时可能是 `undefined`；空闲命令、会话事件中的长任务不能只靠它保证取消。必要时由资源所有者创建独立取消控制器，并在超时、会话关闭或用户取消时触发。

多扩展协作使用明确名称和消息 Schema。工具、命令、状态键、总线事件均避免泛名。底栏、编辑器等整块替换能力是共享界面位置；可以选择一个聚合者、使用独立状态键或声明互斥，不声称不同包天然没有冲突。

## 5. 实现装配：从最小结构起步

### 5.1 选择需要的结构

| 条件 | 建议结构 | 不需要提前建立 |
|---|---|---|
| 一个简单命令或事件 | 单文件，默认导出工厂 | 插件注册框架、业务仓储层 |
| 多入口共享业务规则 | 入口＋业务模块＋对应测试 | 多个重复业务实现 |
| 外部服务或复杂状态 | 加配置/服务适配/状态模块 | 与需求无关的全局容器 |
| 多宿主复用 | 业务核心与 TUI/SDK/RPC 适配分离 | 假想通用 UI 抽象框架 |

命名不固定。职责必须可定位：谁接 Pi，谁做业务计算，谁操作外部系统，谁保存事实，谁负责显示。纯计算尽量不依赖 Pi 上下文，使得核心规则可以独立验证。

### 5.2 一个最小接入形状

下面是 `v0.85.1` 命令扩展的教学构造，展示工厂与运行时回调的区别，不是所有项目都应复制的模板：

```ts
import type { ExtensionAPI } from "@earendil-works/pi-coding-agent";

export default function (pi: ExtensionAPI) {
  pi.registerCommand("project-info", {
    description: "显示当前项目路径",
    handler: async (_args, ctx) => {
      if (ctx.hasUI) {
        ctx.ui.notify(`当前项目：${ctx.cwd}`, "info");
      }
    },
  });
}
```

工厂内注册回调，回调运行时才使用会话上下文。不要在扩展尚未绑定运行时的时候调用 `sendMessage`、`appendEntry` 等动作。临时试用可用 `pi -e ./project-info.ts`，进入 Pi 后执行 `/project-info`；这一步验证命令接入，不验证模型选择工具或跨宿主显示。

此示例只定义 TUI/RPC 通知效果；无 UI 时不输出业务结果。需要 Print/JSON 使用的项目应另外定义结构化结果通道，不能把这份最小代码当作全模式方案。

依赖公开包导出，避免深层导入内部文件。业务文件以目标项目路径为基准，包自带资源以包位置为基准；不要把作者机器绝对路径或 `process.cwd()` 的偶然值写成安装协议。

### 5.3 TUI 先定义信息，再设计外观

按需求从小到大选择：通知/对话框 → 独立 status/widget → 工具与消息渲染 → footer/header 替换 → 自定义组件/浮层 → 编辑器替换。后面的方案接管更多布局与输入责任，不因视觉自由度大就默认选它。

上下文仪表栏至少区分：

- **当前上下文占用**：来自 `ctx.getContextUsage()` 的当前上下文估算及窗口信息；返回缺失或字段未知时显示未知，不记作 0%。
- **累计用量**：明确是当前分支、当前会话或全部历史，分别说明 input/output/cache 口径；它不是窗口占用。
- **费用/额度**：费用估计和订阅额度不是一回事；若额度来自外部服务或本地快照，标明来源与更新时间。

上下文压缩后占用可能减少，累计消耗不因此清零。更换模型后窗口大小可能变化，必须重新计算。

工具卡片区分等待、执行、部分结果、成功、失败、取消；折叠视图保留工具名和结果摘要，展开后才显示参数与细节。渲染函数只负责视图，不在重绘时发请求或写文件。

自定义 UI 必测窄终端、中文宽度、长文本、无颜色/浅色背景、键盘焦点、Esc、重复打开与关闭后输入恢复。使用目标 TUI 的宽度计算和截断工具；ANSI 字符串长度不等于终端显示宽度。`render(width)` 返回值必须遵守宽度与组件合同。

Web 确认弹窗由 Web 宿主实现交互；共用的是业务请求和确认结果合同。将 TUI `custom()` 的组件函数传到 SDK 或 RPC，不会自动得到浏览器弹窗。

### 5.4 交互界面的最小合同

本节适用于状态面板、底栏、浮层和编辑器等界面扩展。先定义以下合同，再选择目标版本的公开接口；无需给每个项目增加一套 UI 框架。

| 决策 | 必须明确 | 验证方式 |
|---|---|---|
| 显示位置与所有权 | 追加独立状态/组件，还是替换完整区域；是否保留原有状态信息 | 与已有扩展组合操作，核对被覆盖内容和恢复对象 |
| 数据来源 | 每个字段的来源、统计范围、未知/过期状态 | 对照同次运行的宿主数据，不凭模型回答或动画推定 |
| 更新与重绘 | 哪些事件更新数据，何时请求重绘；异步结果是否属于当前会话 | 无按键等待也更新；切换会话后不显示旧结果 |
| 操作语义 | 默认状态、开/关/切换、非法参数、重复操作 | on两次仍只出现一次；off两次无异常；错误参数不改变状态 |
| 状态寿命 | 开关在重载、重启、新建/切换会话后保留还是重置 | 每个边界分别操作，与明确约定一致 |
| 清理与恢复 | 谁释放监听/计时器；关闭后恢复哪块界面 | reload、退出、异常初始化后没有重复刷新或残留任务 |

`v0.85.1` 可按以下入口检索：`setStatus` 添加命名状态，`setWidget` 放置独立组件，`setFooter` 替换底栏，`custom` 提供自定义交互。它们接管的区域和输入责任不同；TUI是表现层，Extension负责接入。使用主题颜色不等于另外创建了一份Theme资源。

该版本的 `setFooter(undefined)` 恢复原生底栏，不保证恢复被覆盖的第三方底栏。共享替换区域必须选择一个所有者，或设计明确聚合机制；不能把两个包名称不同当作不会冲突。目标版本事实可查 [custom-footer示例](https://github.com/earendil-works/pi/blob/v0.85.1/packages/coding-agent/examples/extensions/custom-footer.ts)，示例仅作接口参考，不是完整生命周期验收。

刷新优先由实际数据变化驱动。确需计时器时，明确用途、频率、启动与清理时机；不要为了让数字动起来模拟数据，也不要在render中请求模型、发网络请求或写文件。百分比、取整、裁剪与颜色是视图规则，不能反向修改原始测量值。仅TUI功能在其他宿主中应安全跳过，不污染JSON/stdout。

### 5.5 将指南和需求交给开发助手

指南规定方法，需求规定这次的行为。最小任务输入为：本指南、需求文件、目标工作目录、可核验的版本资料、允许写入范围和验收条件。没有完成版源码也应能开始；实现者应主动检索公开类型及官方示例。只有影响行为的缺口才提问，常规代码组织自行决定。

执行顺序：读输入并复述行为合同 → 列实际依赖的接口与证据 → 完成最小可触发版本 → 验证真实使用及失败恢复 → 修正原需求下的问题 → 交给打包环节。每阶段说明已做、失败、未测，不以代码生成或静态检查代替运行。

验收输入与项目说明应分开存放：固定样本不因编写README、生成安装说明或记录结果而改变。冻结输入及预期后，再运行原任务；确需调整样本时重新标识版本并复验，不继承旧通过记录。

检验指南可用性时，让未读过完成版的新上下文只依据上述输入实现一个需求。记录额外追问、首次失败与最终结果；将共性的遗漏补回本指南，将项目特例留在需求文件。独立接手尚未执行时，不宣称指南已通过此项检验，也不保证任意需求一次生成成功。

## 6. 证据验证：每种能力选择自己的判据

### 6.1 所有扩展的最短验证链

1. **目标明确**：冻结代表任务的输入和预期，不能只以模型回复“成功”为预期。
2. **静态检查**：在目标依赖上做类型/模块/资源检查；TS 被加载不等于做过类型检查。
3. **发现与加载**：在隔离资源环境中加载准确入口，确认注册的是本次代码，没有被旧副本覆盖。
4. **调用与结果**：触发真实入口，核对结果内容或实际副作用。
5. **失败与恢复**：至少验证本能力最重要的非法输入、失败或取消；有状态则测试恢复。
6. **按承诺扩展**：只对声明支持的宿主、版本与平台做对应验证，并列出未覆盖项。

### 6.2 按能力增加验证

| 能力 | 正向检查 | 必要反例/边界 | 结果判据 |
|---|---|---|---|
| 事件观察 | 相同触发记录一次有效结果 | 异常、取消、重复触发、无关事件 | 关联 ID 与数量正确，不改变业务 |
| 输入/上下文改写 | 命中条件才改写 | 不命中、扩展自己发送的输入、重复转换 | 正确保留结构，无自触发循环 |
| 调用拦截 | 被允许动作确实执行 | 被拒绝动作、监听器异常 | 被拒绝目标的副作用为零 |
| 命令/快捷键 | 正确输入执行一次 | 非法参数、冲突、执行中重复触发 | 用户操作与实际结果对应 |
| 工具 | 直接执行正确，再验证模型调用 | Schema 外业务非法值、超大结果、服务错误 | content/details/业务效果一致 |
| TUI | 真实终端操作和可见状态 | 窄屏、未知值、取消、焦点、重载 | 显示语义正确且终端可继续使用 |
| 会话状态 | 保存后新进程恢复 | 切分支、旧数据、损坏记录、在途请求 | 正确分支数据，无串写和重复副作用 |
| Provider | 正常调用及流结束 | 认证失败、空目录、刷新取消、异常流 | 正确消息序列与错误边界 |
| 外部集成 | 真实服务代表任务 | 超时、部分成功、断连、重试 | 外部结果与本地状态可核对 |
| 组合扩展 | 同时加载后各自正常 | 同名、共享底栏、重复监听、加载顺序 | 冲突可见，选择与清理有确定结果 |

真实模型调用用于检验工具描述、模型选择和结果消费，不替代确定性的业务规则测试。文本快照和渲染测试也不替代真实终端输入、生命周期与交互验证。

验收规范与当前授权范围不一致时，先列出差额：哪些本轮可执行，哪些因缺权限或环境保留未测。不得擅自扩大安装作用域、修改门禁使其通过，或把未授权项填写为不适用。局部通过与整体未放行可以同时成立。

### 6.3 修改已有扩展时

先复现需要改变的行为，再标出受影响入口、状态与使用者；保留一个未改变行为的验证。修改状态格式时考虑旧会话；修改工具输出时检查模型、渲染器与宿主；修改取消方式时检查外部任务是否真的终止。不要重写无关目录来“统一架构”。

证据记录采用：`对象版本/哈希、环境、输入、预期、实际、通过/失败/未验、证据位置`。无模型、替身服务、静态源码和真实调用分别注明。失败项不能因其他项通过而被覆盖。

## 7. 交付演进：让下一位使用者能够接手

开发完成后向打包环节提供：默认导出入口及关联文件、外部运行依赖、包内资源、支持环境、配置项与秘密的注入方式、状态存储/升级策略、代表任务与验证记录。

兼容声明写成具体范围，例如“在 Pi 0.85.1 的 TUI 中完成了指定验证；RPC 自定义组件不支持；其他版本未验证”。后来验证了其他版本再扩展范围。不要用“支持全部 0.x”代替证据，也不要求用户为了使用方法论永远降级到 0.85.1。

出现以下变化时重新打开相应决策：入口或宿主变化 → 运行映射；数据结构变化 → 状态合同；外部 API 变化 → 服务适配与失败验证；依赖/分发变化 → Package 验证。对升级差异没有影响的章节无需重写。

## 8. 用不同需求检查方法是否足够通用

以下均是推演任务，不是已通过运行的案例：

| 需求 | 应得到的设计 | 错误路线 |
|---|---|---|
| 记录工具耗时 | 事件关联＋可选外部追踪；不必新增工具 | 每观察一次都要求模型调用一个统计工具 |
| 展示上下文仪表栏 | 数据口径＋TUI 显示＋未知态/重载验证 | 累计 tokens 除以窗口大小 |
| 创建可恢复待办 | 状态权威＋当前分支重建＋工具或命令入口 | 把模块全局数组当持久化 |
| 接入内部服务 | 输入/授权/错误合同＋服务适配＋实际结果核对 | 只要 fetch 返回 200 就声明业务成功 |
| 给浏览器增加确认 | 共享业务合同＋宿主实现交互与超时 | 仅复制 TUI 浮层代码 |
| 动态发现模型 | Provider/资源生命周期＋超时和刷新契约 | 在工厂中启动永久后台监听且无关闭者 |

如果新需求找不到入口，先判断是遗漏的公开能力、需要宿主自建，还是框架不支持；不能永远塞入“其他扩展”。如果新案例改变了原有决策边界，应更新方法，而不只补一段例子。
