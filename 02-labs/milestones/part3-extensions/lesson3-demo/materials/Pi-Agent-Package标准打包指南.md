# Pi Agent Package 标准打包指南

> 文档性质：自研开发方法与交付约定，“标准”不是 Pi 官方认证或兼容性承诺。已完成主控源码核查；文中最小命令与清单组合在 Pi 0.85.1 隔离环境完成了 npm 打包、解压换目录、自动加载和 RPC 命令通知验证，入口缺失反例也已验证。尚未完成独立审查、新助手依据指南开发未见需求、TUI 实操及跨版本/平台验证；不能把最小示例的结果外推到全部能力。

本指南用于把已经开发的 Pi 能力交付给其他使用者：明确交付内容、组织资源、处理依赖、生成产物、验证安装，并管理更新与退出。可以单独交给编程助手使用，不依赖某个课堂案例或作者机器目录。

**打包方法跨项目复用；Pi 清单、命令与加载规则以 `v0.85.1` 为参考。目标版本变化时重新核对所用规则，不能只替换版本号。**参考源码为官方发布提交 `d981de1229ef899957bbe968bc8dcda02a21f477`，核验日期为 2026-09-21。

本指南不负责设计扩展业务；需要从需求创建能力时，先用 [Extensions 标准开发指南](./Pi-Agent-Extensions标准开发指南.md)。Package 可以包含一个或多个 Extensions，也可以携带其他受支持资源；不要求为了“完整”创建空的 Skills、Prompts 或 Themes 目录。

## 1. 从交付对象开始，而不是先压缩目录

先读取现有项目、入口和验证记录，明确使用者拿到什么、在哪里运行、如何确认生效。已授权的构建和本地验证直接执行；公开发布、推送或真实业务操作仍依当前任务授权。

| 输入 | 要明确的内容 | 不明确时的最小动作 |
|---|---|---|
| 交付能力 | 扩展入口、附带资源、必需与可选组件 | 列实际被引用的文件，删除清单中的空想能力 |
| 使用环境 | Pi 版本、CLI/SDK/RPC 宿主、平台、运行时 | 检查目标环境及扩展的支持范围 |
| 交付渠道 | 本地目录/课程压缩包、npm、Git | 按使用者获取方式选择，不默认发布 npm |
| 安装作用域 | 项目级还是用户级，是否可影响已有扩展 | 默认在隔离项目验证，正式作用域由需求决定 |
| 运行条件 | 外部依赖、环境变量、数据、网络、系统命令 | 区分可自动安装和必须另行准备的内容 |
| 验收任务 | 至少一个可确定预期的能力调用 | 复用开发验收，不用“安装成功”替代业务效果 |

核心模型是五份信息保持一致：**声明要交付的资源 → 实际进入产物的文件 → 使用者能解析的依赖 → Pi 实际加载的入口 → 能力产生的可观察结果。**任何一环断开，压缩包和安装命令都可能成功，能力仍不可用。

## 2. 选择分发形式

### 2.1 选择原则

| 形式 | 适合情况 | 成本与边界 |
|---|---|---|
| 单个扩展文件 | 无额外资源与第三方依赖的小扩展 | 便于试用；逐渐出现资源和依赖后应转目录 |
| 本地 Package 目录或解压包 | 课程、内部分发、离线交接、人工检查 | 要交代解压位置、依赖安装和路径保持 |
| npm 包 | 有版本号、需要安装/更新渠道 | 要验证 npm 实际产物和消费者安装；发布需授权 |
| Git 包 | 用 tag/commit 分发源码或成品 | 要验证 checkout 后可用，不能依赖作者未提交文件 |

先让选定渠道在干净环境中成功一次，再增加另一条渠道。支持 npm 不自动证明 Git 安装可用，Git 仓库可运行也不证明 npm `files` 包含了所有资源。

### 2.2 本地路径不是复制安装

`v0.85.1` 的本地路径安装将路径记录到设置，不复制整个目录，也不自动完成普通本地目录的依赖安装。移动或删除源目录后可能失效；相对路径从所在设置文件解析。

因此，课程 ZIP 或 npm 生成的 `.tgz` 应先解压，再按照目录方案安装。**不要把 `pi install ./something.tgz` 当作原生解压安装协议。**本地文件路径可能被当作单个扩展入口，不能从命令退出码判断压缩包已正确安装。

下面是参考形式，`/absolute/path/to/...`、`@scope/...`、`owner/...` 都是示意值，执行前替换成实际目标：

```bash
# 已解压、入口与依赖已经准备好的本地包
pi install -l /absolute/path/to/my-pi-package

# npm：明确固定包版本
pi install -l npm:@scope/my-pi-package@1.0.0

# Git：固定需要交付的tag或commit
pi install -l git:github.com/owner/my-pi-package@v1.0.0
```

`-l` 写入项目设置；省略它则使用用户设置。正式使用前核对当前项目与作用域。设置存在不代表已经允许加载项目资源，仍需遵守该版本的项目信任机制。新消费目录启动时检查实际信任状态：默认询问且无适用信任记录时会出现提示；只有审阅资源并确认目录后才接受。拒绝后不加载项目资源是预期边界，不能因此判定包损坏。父目录已有信任决定或默认策略不同可能不再询问，不以“必须看到弹窗”作为通过条件。

## 3. 组织 Package：发现清单和文件清单分别管理

### 3.1 最小结构由运行入口决定

```text
my-pi-package/
├── package.json
├── README.md
├── LICENSE                 # 对外分发时明确代码及附带资源的许可
├── extensions/
│   └── project-info.ts     # 默认导出的扩展工厂
└── assets/                 # 仅在扩展实际引用资源时存在
```

业务复杂时可以有 `src/`、`dist/`、`tests/`，但 Pi 只应发现真正的扩展入口。辅助模块、测试、实验脚本不能因为放在扫描目录里就被当成独立扩展加载。

教学构造清单：

```json
{
  "name": "my-pi-package",
  "version": "0.1.0",
  "description": "A project information extension for Pi",
  "type": "module",
  "keywords": ["pi-package"],
  "files": ["extensions", "README.md", "LICENSE"],
  "pi": {
    "extensions": ["./extensions/project-info.ts"]
  },
  "peerDependencies": {
    "@earendil-works/pi-coding-agent": "*"
  }
}
```

名字、版本、描述、许可与入口均按真实项目确定。此例没有第三方运行依赖；需要资源时同时修改 `files` 和资源引用。`keywords` 用于发现，不证明可加载或安全；不准备发布时也不必为了展示元数据创建图片和视频。

### 3.2 两份清单各自回答一个问题

- `pi.extensions` 等字段：**Pi 从包里发现哪些能力**。
- npm `files`、忽略规则和实际 tarball：**使用者收到哪些文件**。

`pi` 指向了入口，不会自动保证 npm 将入口打进去。`files` 收录了代码，也不会自动把它注册为 Pi 扩展。验收时对照两者和实际压缩包内容。

在 `v0.85.1` 中，有 `pi` manifest 时按 manifest 解析；没有时才采用约定目录发现 `extensions/`、`skills/`、`prompts/`、`themes/`。不要把“manifest 少写一个字段”当作该资源会自动回退到约定目录。路径相对包根目录；复杂 glob、点目录、符号链接先验证实际匹配，简单包优先明确入口文件。

多资源包须逐类核对“源文件 → 实际归档路径 → 对应pi资源字段 → 安装后的真实入口”。例如交付模板时，实际tarball必须含模板文件，files清单必须收录它，pi.prompts必须明确指向该资源，并在新项目实际调用。不要将上面的单Extension清单原样当作多资源包清单。

如果交付额外资源，只添加实际需要的字段：`skills` 指向对应技能资源，`prompts` 指向提示词资源，`themes` 指向主题资源。此处只负责资源进入产物及被发现，不要求开发者重新学习这些资源的一般定义。

## 4. 依赖合同：谁提供什么，必须说清楚

### 4.1 四类依赖不要混用

| 类别 | 处理方式 | 验证重点 |
|---|---|---|
| Pi 提供的核心包 | 按目标版本官方要求放在 peerDependencies，避免重复打包 | 实際加载的是宿主提供的 API |
| 普通第三方运行库 | 放 dependencies | 使用者安装时能取得，不只存在于作者 node_modules |
| 开发/测试/构建工具 | 放 devDependencies | 生产安装不依赖未安装的开发工具 |
| 非 npm 条件 | 系统命令、服务、模型、环境变量、浏览器等写进使用说明 | 可检测缺失，错误明确；没有把凭据打入产物 |

`v0.85.1` 文档要求核心包使用 `peerDependencies: "*"` 并不捆绑，涉及 `@earendil-works/pi-ai`、`pi-agent-core`、`pi-coding-agent`、`pi-tui` 和 `typebox`；只声明实际导入的包。开发时另用明确版本的开发依赖核对类型。

这里的 `"*"` 是宿主依赖装配方式，**不是“全部 Pi 版本已兼容”的声明**。Pi 管理的 npm 安装还会避免自动解析宿主 peers，不能指望 peer 范围替代兼容检查。支持版本、宿主和实际验证范围写在 README 中；核心能力缺失时提供明确错误或不支持说明。

需要另一份 Pi Package 的资源时，不能只把它当普通库安装后假设 Pi 自动发现。在该版本官方分发方式下，将其加入 `dependencies` 与 `bundledDependencies`，再在 `pi` 中明确引用它位于 `node_modules/` 的资源。纯函数库不需要因为被 Extension 使用就成为 Pi Package。

### 4.2 直接分发 TS 与分发构建产物

| 方案 | 应做什么 | 典型失败 |
|---|---|---|
| 直接 TS | 收录入口、全部被导入模块和运行资源，声明运行依赖 | 入口有了，旁边的模块或数据没打进去 |
| 编译 JS | 构建后 manifest 指向存在的输出，保留 ESM/默认导出及资源位置 | 清单仍指向源码；运行时路径只在源码布局成立 |
| Bundle | 核对宿主核心包 external、动态导入、原生模块和资源 | 重复打入宿主模块，或构建器漏掉运行期文件 |

选择构建不是兼容性保险。TS 与 JS 都可能依赖变化的 API；bundle 也不会冻结宿主的事件语义。

Git 安装要单独注意：参考版本默认在仓库中安装生产依赖，构建脚本若要求被省略的 devDependencies 会失败。可选择提交可直接运行的 TS、提交必要构建产物，或明确提供已验证的构建路径。不能假设作者的 `prepack` 在所有 Git 安装路径上都会产生相同产物。

锁文件只能约束它实际参与的安装流程。`npm ci` 适合包含匹配锁文件的源码/目录交付；没有锁文件就不能照抄该命令。消费者安装 npm 包时也不能假设作者开发目录的锁文件控制了所有依赖解析。

### 4.3 路径和状态不依赖作者环境

包内只读资源以包/模块位置解析；业务项目文件以明确的目标工作目录解析；持久化状态使用声明的项目级或用户级位置。不要把安装目录当成业务数据库，也不把修改安装包中的文件作为配置接口。

跨平台时检查大小写、空格路径、分隔符、shell 及外部可执行程序。需要离线交付时，在断网条件下验证全部运行依赖和资源已准备；仅复制一个 `node_modules` 目录不能证明跨操作系统或 CPU 架构兼容。

### 4.4 区分练习工程与宿主安装包

源码练习工程可以通过固定版本的开发依赖提供本地Pi、类型检查和测试工具；面向已有Pi的安装包应按目标版本要求声明宿主核心peer依赖，只将真正的第三方运行库放入dependencies。不得把“练习工程npm ci后能启动自己的Pi”直接当作“包已能安装到使用者已有Pi”。

可以保留一个源码项目，用明确files清单生成精简分发物，不强制维护两套实现。README分别写清源码开发、产物解压安装和实际启动入口；声明的目标宿主来自真实验收。调整依赖分类后，更新锁文件、重建产物，再从新产物验证，旧证据不自动继承。

## 5. 生成产物：检查使用者真正拿到的东西

执行顺序按所选渠道裁剪：

1. 固定扩展源码与版本，确认开发验收的对象和本次待打包对象一致。
2. 根据项目实际脚本完成类型检查、必要测试及构建。
3. 核对 manifest 中每个入口、导入模块、运行资源和依赖。
4. 检查分发文件列表，再生成准确产物。
5. 从产物解出或安装到全新目录，按下一节验证。

在已检查 package scripts 的包根目录中，可使用：

```bash
npm pack --dry-run --json
npm pack --json
```

它们检查/生成 npm 产物，并不发布到 registry。命令可能执行包声明的生命周期脚本，所以应先看脚本做什么；不要把 dry-run 当成所有操作都无副作用。

核查实际文件清单：入口、资源和说明是否存在；是否混入 `.env`、认证文件、会话历史、业务数据、临时日志、作者绝对路径或无关大文件。第三方代码与媒体应保留适用许可与来源要求。这里只检查实际分发责任，不把模型意见当法律结论。

记录文件名、包名/版本及 SHA-256。新构建得到不同字节时是新的待验收对象，不继承旧 tarball 的成功结论。

## 6. 使用者验收：从干净环境走完整一条链

### 6.1 创建验证环境

至少满足：新的工作目录、单独的 Pi 配置目录、明确的 Pi 可执行文件和版本、没有作者全局扩展掩盖缺失。参考版本可用 `PI_CODING_AGENT_DIR` 指定隔离用户配置目录；不要重定义 `HOME` 或复制真实凭据。

示意命令使用待替换的绝对路径：

```bash
PI_CODING_AGENT_DIR=/absolute/path/to/test-agent pi --version
PI_CODING_AGENT_DIR=/absolute/path/to/test-agent pi install -l /absolute/path/to/unpacked-package
PI_CODING_AGENT_DIR=/absolute/path/to/test-agent pi list
```

以上操作必须在新建的验证项目目录执行。之后启动、`pi list`、更新和移除都使用同一个隔离配置目录与项目目录。依赖安装按 README 完成，不能偷偷借用作者开发环境。使用 `--no-extensions -e ...` 可以检查单个明确入口，但它不验证普通启动时的自动发现；交付验收还必须测普通启动。

### 6.2 分层检查及通过标准

| 检查 | 操作 | 通过标准 | 不足以证明 |
|---|---|---|---|
| 产物身份 | 从实际分发物安装或解压 | 包名、版本、哈希对应本次交付 | 能力可用 |
| 依赖解析 | 使用说明中的安装步骤 | 没有隐含全局模块/本机路径 | Pi 发现入口 |
| 发现加载 | 正常启动目标 Pi，检查资源与错误 | 准确入口加载，无旧副本掩盖或重复 | 模型已调用 |
| 注册生效 | 检查对应命令、工具、状态或事件 | 能力可见或收到准确事件 | 业务结果正确 |
| 代表任务 | 执行明确输入 | 输出、状态和实际副作用符合预期 | 所有模型和平台通过 |
| 负向行为 | 缺依赖/配置、拒绝、超时、异常数据 | 错误明确且无错误副作用 | 更新与卸载可用 |
| 再次启动 | 新进程恢复或重载 | 必要状态正确，注册不重复 | 全部跨版本兼容 |

无模型命令可以先验证真实注册和执行；依赖模型决策的能力还要补实际模型调用。TUI 包需要真实终端操作，SDK 包需要实际宿主消费。只展示已安装列表不能作为扩展运行验收。

### 6.3 必测反例按项目选择

- **换目录**：仅从实际交付物建立新副本，确认不依赖作者源目录。
- **漏资源**：临时测试副本中移除一个必需资源，确认能检测失败；不要改正式产物。
- **缺依赖**：证明错误能定位到未满足的运行条件，而不是卡住或静默降级成功。
- **多包共存**：命名、工具覆盖、底栏与状态位置有无冲突；独立模块根不等于公共注册名隔离。
- **作用域覆盖**：项目/用户设置同时存在时，确认实际加载哪一份，禁用是否生效。
- **版本变化**：至少验证所声称支持的目标版本；未测版本保持未知。

验证记录只需准确包含环境、产物身份、输入/预期/实际、结果与未验项。无需为了文档完整虚构固定数量的测试。

## 7. 安装、配置、升级、移除的合同

### 7.1 把配置与代码分开

README 写清每个配置的含义、默认行为、是否必需、读取时机和错误表现。秘密只说明如何提供，不放真实值；若缺少可选服务，哪些能力可用、哪些明确不可用要可观察。

消费者可以通过设置中的 package 对象过滤资源。`v0.85.1` 中，省略类型字段表示该类型按包允许范围加载，`[]` 表示该类型不加载；`!pattern`、`+path`、`-path` 有各自匹配规则。过滤基于包资源声明，不能作为凭空加载未交付资源的办法。

`pi config` 可管理启用/禁用，`pi config -l` 进入项目覆盖。项目和用户的同一包按身份去重，普通项目项优先；`autoload: false` 有增量覆盖语义。不要手动叠加路径后假设会执行两次或自动合并两版。

### 7.2 更新时分清三种版本

分别记录 **Pi 宿主版本、你的 Package 版本、第三方依赖版本**。只更新包不一定升级 Pi；升级 Pi 也不意味着所有扩展被同步升级。

参考版本命令的含义：

| 命令 | `v0.85.1` 含义 |
|---|---|
| `pi update` | 更新 Pi 本体 |
| `pi update --extensions` | 更新包，并核对固定 Git 引用 |
| `pi update --all` | 同时处理 Pi 与包 |
| `pi update npm:@scope/my-pi-package` | 更新指定包；名称是示意值 |

固定精确 npm 版本的包不会因常规包更新自动追新。固定 Git tag/commit 也不会自动变成新引用，但更新操作可以把本地 clone 恢复到所配置引用；不要在包管理器维护的 clone 中存个人修改。变更固定目标时使用新的明确安装规格。

升级前确定准确旧产物或旧引用、配置与业务状态备份；新版本在隔离环境中验证后再切换。状态结构升级不可逆时，仅把代码回退不一定能恢复业务，必须另有数据迁移/恢复策略。更新失败后应说明当前实际版本，而不是只给“回滚成功”的文案。

### 7.3 移除不是删除全部业务数据

参考命令 `pi remove -l npm:@scope/my-pi-package` 中的包名须替换成实际已安装包，作用域与安装保持一致。移除设置、卸载包、结束当前进程中已加载的能力以及清理业务数据是不同动作。

在测试环境移除后，以新进程确认能力不再加载；当前会话需按实际宿主支持进行重载或退出。检查扩展自己的后台资源停止。业务数据默认按需求保留，不因卸载自动删除；若提供清理功能，明确具体路径、所有者与单独授权。

### 7.4 同类扩展的切换与恢复

切换前盘点包登记、用户/项目自动发现目录和启动参数中的显式入口；`pi list`不是所有已加载扩展的完整证明。一个源码桥接文件和一份新Package可能注册相同能力，即使包管理器没有重复包记录。

先在独立演示配置与新项目中验证：原生状态 → 新包 → 停用新包 → 原生状态；随后再验证与日常组合共存。隔离示范不代替普通启动和完整组合验收。认证由使用者通过受支持方式配置，不复制真实认证文件进入交付物。

涉及底栏/编辑器等整块替换时，只启用一个所有者。切换顺序为：结束当前操作、记录旧入口 → 停用准确旧入口 → 启用新入口 → 重启并核对实际版本与功能 → 按需恢复旧入口。停用、卸载登记、删除源码、清除数据是不同动作，教学演示优先可恢复停用，不要求删除使用者已有扩展。

课堂最小版与完整版本分别记录包名、版本、来源及验证范围。新版尚未验收不得覆盖已验证分发物；最终从实际归档走一遍安装、使用、移除和重启。

## 8. 最终使用说明必须自足

一份简洁 README 应回答：

1. 这个包提供什么、适用什么任务，以及不支持什么。
2. 已验证的 Pi 版本、宿主、平台与必要依赖。
3. 从本次交付物安装的准确步骤及项目/用户作用域。
4. 配置项和凭据注入方式，不包含真实秘密。
5. 一条代表任务及可观察预期，如何查看加载/错误信息。
6. 状态保存在哪里，如何更新、退出、移除与必要恢复。
7. 已验证、失败、未验证分别是什么。

交付压缩包时，将必要使用说明放入包内；不能要求使用者先找到作者的课堂目录。提供“可运行包”意味着依赖、配置和入口有可执行路径，不意味着必须把所有二进制和账号一起打包。

## 9. 正例与反例：检验打包方法是否适用

以下是教学推演：

| 情况 | 正确决策 | 应拒绝的完成声明 |
|---|---|---|
| 无依赖命令扩展 | 单入口 TS＋最小说明；临时试用或目录安装 | 因为没有 build 脚本就称为未完成 |
| 多文件 TUI 扩展 | 入口/模块/资源全部进入产物；宿主 TUI 依赖不重复 bundle | 打包文件存在就称终端交互通过 |
| npm 内包含另一个 Pi 包的资源 | 明确捆绑及资源路径，核查 tarball | dependencies 有包名就称它的能力会自动加载 |
| Git 包只提交源码且依赖构建 | 验证生产依赖安装路径，调整成可直接运行或可靠构建 | 作者运行过 prepack 就称 Git 用户能用 |
| 用户把本地目录移动 | 重新指向实际路径并检查发现 | 原来的 pi list 有记录就称仍安装正常 |
| 未来小版本发布 | 检查受影响接口、包规则和代表任务 | TS 文件没有改动就称所有版本兼容 |
