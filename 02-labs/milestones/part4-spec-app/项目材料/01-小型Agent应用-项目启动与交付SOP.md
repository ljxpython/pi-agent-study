# 小型 Agent 应用：项目启动与交付 SOP

版本：1.2（2026-09-23案例状态校正）。适用对象：准备借助开发 Agent 完成一个小型前后端应用的学习者。

本手册用“Pi 工单问答助手”说明如何准备、决策、分步开发和验收。它是操作流程，不是安装手册或完整接口规范；功能和接口以项目自己的需求设计文档为准。配套使用[项目启动卡与执行模板](./02-工单问答助手-项目启动卡与执行模板.md)。

本文不依赖先前聊天或特定机器；示例是教学设计，所有检查结果都需要实际执行后填写。

## 1. 从什么问题开始

项目目标：用户配置自己的模型，选择一份工单资料，通过对话查询问题、核对记录和建议，确认后保存报告，再次打开应用能继续使用。

学习目标：你能解释一次请求经过哪些位置，借助 Agent 完成开发，修改一项规则，并用正确和错误输入证明修改有效。

分别检查两个目标：应用能用，要有真实业务结果；自己学会，要有独立修改和验证。看到漂亮页面、收到一段回答或解压完成版运行，都不能单独证明二者达成。

## 2. 开始前准备什么

| 准备项 | 最小内容 | 缺少时怎么办 |
|---|---|---|
| 启动卡 | 用户、任务、范围、成功标准、当前未知 | 先填写配套启动卡，不让Agent猜关键目标 |
| 需求设计 | 页面、状态、数据结构、接口、验收与版本 | 可先做准备；实施前补齐并确定一个唯一版本 |
| 数据 | 默认示例、独立上传样例、错误样例与各自预期 | 先构造教学样本，不用真实客户数据替代 |
| 工程输入 | 项目目录、依赖锁文件、能力包或其源码、版本说明 | 核对来源与可用性；缺包不宣称业务接入完成 |
| 模型接入 | 可用接入方式、支持的协议、测试预算 | 凭据在配置时输入；缺少接入仍可做页面和数据校验 |
| 成果样例 | 查询记录、报告草稿、保存后的阅读效果 | 先写一份示例，确认用户能否理解 |
| 验收环境 | 操作系统、浏览器、运行时、复现者 | 未测试的平台只标未验证，不推定兼容 |

新项目可以约定将需求设计放在 `docs/project-spec.md`；本案例已有项目需求与前后端 Spec，学员以随课分发副本的实际文件和 README 为准。这两份流程文档本身不包含完整源码、依赖或模型配置，不能仅凭文件名推定练习材料齐备。

## 3. 先把任务讲具体，再讨论实现

按以下顺序推演一位用户的完整操作：

1. 第一次打开，是否知道需要配置模型？配置失败能否继续修正？
2. 是否知道当前选择了哪份资料、资料包含什么？
3. 是否理解“查看能力”和“把能力加入任务”的区别？
4. 发送后，能否看懂正在回复、工具执行或等待确认？
5. 结果出现后，能否核对记录、数量与来源？
6. 是否知道报告只是草稿，还是已经实际保存？
7. 刷新或重启后，能否继续使用，旧确认是否失效？

每一步写出“用户动作→系统响应→可以检查的结果”。如果只能写“体验良好”“智能回答”，说明还需要具体化。

本案例不要求每轮都产生文件：普通问答只回复；查询产生结构化记录；用户要求报告且批准保存后，才出现已保存成果。

## 4. 决定第一版做多大

本案例第一版：本地单用户、一个活动会话、同一时间一个请求；极简三栏；模型设置；同结构工单JSON上传；资源详情与选择；真实查询；报告确认保存；状态恢复。

暂不包含多人账户、任意文档解析、可执行插件上传、工作流画布或公网部署。需要这些能力时，先写新的用户任务和验收，再评估对现有设计的影响。

每个新增想法先回答四个问题：

- 它解决当前哪一步的具体问题？
- 不做时，用户是否无法完成主任务？
- 已有能力或更小改动能否覆盖？
- 除开发外，还会增加哪些测试、说明和维护成本？

例如：模型设置和资料上传直接帮助用户独立使用，属于本版范围；任意格式解析扩大了适用面，也增加解析质量和错误恢复成本，可以后置。不要为了未来可能的需求提前更换整套技术。

## 5. 先做可检查的交互，再定视觉细节

本案例三栏默认展开，两侧可调宽或收起，对话居中于剩余区域。资料名称点击看详情；添加按钮与拖入输入区只选择资料；移除标签不删除文件。模板与Skill从能力库/命令进入，工具内置，不拖拽授权。无资料也可问应用职责和用法。

至少准备以下状态：

| 状态 | 用户应看见什么 | 必须避免 |
|---|---|---|
| 未配置模型 | 设置入口、缺少的信息 | 整页无法打开或假装模型已连接 |
| 未选择资料 | 当前无资料、可选/可上传入口 | 悄悄使用另一份默认资料 |
| 已选择 | 资料名和能力标签 | 上传成功就等同本轮已使用 |
| 执行中 | 当前动作、停止入口 | 重复提交或运行中静默更换模型/资料 |
| 等待保存确认 | 可读的不可变草稿、确认与取消 | 等待模型最终回答后才显示确认，造成互相等待 |
| 查询完成 | 结论、记录、数量、来源 | 从自然语言中猜业务数据 |
| 保存完成 | 实际保存并回读的报告 | 收到批准就显示“已保存” |
| 失败或中断 | 哪一步失败、已有结果、下一步 | 把失败包装成空结果或自动重放写入 |
| 恢复 | 当前会话、选择、已有报告 | 让旧的待确认动作重新变得可批准 |

先用明确标记的模拟状态检查操作顺序和内容。确认这些能表达清楚后，再统一配色、间距和动画；模拟状态不能作为业务执行证据。

## 6. 提前准备数据与答案

数据至少分为四组：默认基线、独立上传样本、非法输入、边界情况。预期答案应在运行前确定，不从程序输出反推答案。

本案例默认基线的典型预期为：平台团队open工单得到T01/T04/T06，加入urgent条件后得到T01；前端团队closed得到成功空结果。只有数据内容与已约定基线相同时才能使用这些答案。

独立上传样本使用U01，查询应只返回U01，再切回默认资料应恢复基线结果。这一对操作用来排除“页面换了名字，后端仍读旧数据”的问题。

负例包括非法JSON、缺少必要字段、重复ID、错误类型、非法枚举、超出约定体积或条数。用户不能通过文件名指定服务器路径。上传资料只能作为业务数据，不能变成可执行代码。

## 7. 先验证三个最容易返工的假设

以下实验按进入条件执行，不要求在任何开发之前全部完成。

| 假设与时机 | 最小实验 | 成立所需证据 | 不成立时处理 |
|---|---|---|---|
| 模型可支持业务；SDK接入阶段 | 同一配置完成问答和无副作用工具调用 | 实际模型身份、真实工具请求和结果 | 检查协议/工具兼容；不能仅凭聊天通过开放业务 |
| 选择确实控制输入；资料接入阶段 | U01查询→切回基线→重新查询 | 两次不同预期及各自来源 | 检查后端绑定与缓存；不靠调整界面修饰结果 |
| 新用户理解交互；原型及联调阶段 | 让未参与设计的人查看并选择资料、使用任务入口、查询、保存 | 观察操作、求助位置与任务结果 | 先定位名称、反馈或流程问题，再改动复测 |

每次实验先记录假设、预算、通过条件和失败条件。样本不足或环境失败时写“证据不足”，不能直接判定方案可行或不可行。

只有模拟页面时，用户观察可以验证操作理解；它不能证明模型、后端或保存功能可用。后续必须重走真实链路。

## 8. 按里程碑推进

| 节点 | 做什么 | 验收后才能认定的成果 | 失败时先看哪里 |
|---|---|---|---|
| M0 起点 | 核对目录、环境、输入和版本，建立最小骨架 | 起点可复现、样本和目标明确 | 环境、依赖、缺失输入 |
| M1 页面 | 三栏、状态、设置/详情入口和选择交互 | 页面流程可检查 | 标签、状态、布局、交互反馈 |
| M2 底座 | 独立接入Pi SDK、配置和模型探针 | 同一会话真实两轮问答、工具探针通过 | 认证、协议、模型、SDK接线 |
| M3 联通 | 浏览器→后端→SDK→事件→浏览器 | 真实问答、失败、停止和防重复提交 | 请求与事件对应关系 |
| M4 业务 | 上传、资料选择、能力限制和查询 | 实际读取所选资料，结果与独立预期一致 | 参数、资料版本、工具集合、业务函数 |
| M5 写入 | 草稿、确认、取消、保存与回读 | 确认只写一次，取消不写，失败不假成功 | 动作绑定、一次消费、磁盘结果 |
| M6 交付 | 刷新/重启恢复、独立运行与微改 | 换目录可复现，另一人能接手 | 隐藏配置、绝对路径、恢复与说明缺口 |

M1与M2可在明确文件归属后独立推进，M3依赖二者。不要先精修全部页面才尝试SDK，也不要因底层探针通过而省略真实浏览器验证。

已有工程先复现并核对差异；空项目按节点逐步构建。不要删除有效代码制造“从零开发”过程。阶段版可以用独立副本形成。

## 9. 人与Agent如何分工

项目负责人确定用户目标、关键取舍、预算和完成标准；开发Agent实施明确范围内的修改；验证者按预先确定的标准检查实际产物。同一个人可以承担多个角色，但实现和验证仍要区分。

每个任务交接至少包括：目标、已满足输入、允许修改的文件、保护对象、步骤、验收、停止条件。共享类型、锁文件、需求主文档、端口和状态目录在同一阶段只能有一个明确写入者。

关键选择未知时，先做不依赖它的工作。真实凭据不写进任务卡、提示词、截图或分发物；在需要时通过应用设置或约定的私有配置输入。

不要重复询问已确定的布局和业务范围。遇到新需求、权限扩大、无法安全恢复的动作或真正阻塞时，只处理受影响部分，并说明缺失信息改变什么决定。

## 10. 出错时怎样继续

| 现象 | 首先检查 | 继续条件 |
|---|---|---|
| 设置显示成功但无法提问 | 已保存与已应用是否分开，实际调用配置是否一致 | 真实请求通过；失败保留旧可用配置 |
| 可以聊天但没有工具结果 | 工具是否加载、允许集合、模型是否支持调用 | 工具真实执行且返回结构化结果 |
| 换资料后答案不变 | 请求绑定的资料ID/版本与旧查询缓存 | U01与基线分别符合预期 |
| 点击确认后没有文件 | 批准、工具完成、实际写入、回读是否一致 | 以文件事实判定，不盲目重复保存 |
| 刷新后结果不明 | 后端状态与现有报告 | 先核对结果，再决定下一动作 |
| 重启后无法继续 | 会话与状态位置、当前配置、资料是否可用 | 恢复后执行一次真实后续任务 |

鉴权失败先检查授权和配置，不在同一条件下无限重试。网络重试应有次数或时间预算；有副作用的动作必须先确认是否已执行。停止不等于撤销已经完成的写入。

## 11. 用最少文档留下可复用过程

项目需求设计维护目标行为；README维护实际安装与操作；验证记录维护实际结果。阶段决策追加到项目需求设计的过程记录区，不另建内容相同的多份PRD。

每个阶段记录：起点与目标→真实问题→备选与选择理由→修改范围→预期和实际→未验证项→下一步。没有尝试过的方案写“备选”，不能写成“失败经历”。

保留关键失败、最终证据和可运行入口，清理本次重复临时产物前先检查依赖。不要用大量原始聊天和日志代替解释。

## 12. 何时可以交给别人

- 从干净目录按README运行，使用接手者自己的配置。
- 查、保存、取消、失败和恢复都有实际验证，结果关联到被测版本。
- 另一人能独立完成一项微改，并说清为什么改这些位置。
- 包内没有密钥、个人会话、私人路径、用户上传资料或无关日志。
- 未测试的平台、模型和场景明确列出，不扩大兼容承诺。

流程文档完成、代码构建通过、真实业务通过、独立接手通过是不同状态，分别记录。

## 13. 现在先做什么

第一步，读取随课项目的当前需求、Spec 与 README，核对目标环境、真实模型接入方式和练习预算；已有产品决定直接沿用，不重做已实现工程。

第二步，准备主流程脚本、独立数据样本、错误样本和报告示例。先判断结果应该是什么，再让Agent写实现。

第三步，从当前工程复制明确标注的隔离练习副本，先复现一条已有主流程，再只修改本次指定的小范围需求，按对应 M 节点和正反例验收。

暂时缺少模型接入时可以准备需求、数据和离线练习，不声称本机真实调用已通过。本案例报告已采用 Markdown 保存与下载；换业务或部署范围时，先更新需求和验证，再讨论功能扩展。

案例进度随工程迭代，当前事实以[002项目入口](../../../../../../04-项目设计制作/002-Pi工单问答助手/00-项目入口.md)与[PLAN](../../../../../../04-项目设计制作/002-Pi工单问答助手/04-执行过程/PLAN.md)为准。M2—M6已有本机验收记录，不代表学员机器或新改动已通过；决策保留文字与编号图片，不要求逐版代码快照。课堂练习按随课副本与当次任务授权进行。
