# 工单问答助手｜从设计反馈到可靠交付

本页按原项目的需求、阶段计划、工程复盘与验收记录整理，帮助学员把一次工单助手开发迁移到自己的小项目。它不是完整聊天记录或生产发布结论；项目不同阶段的“已实现”“待实现”请按日期及[阅读入口](../00-项目入口.md)区分。

## 五个改变开发方向的决定

1. **先确认用户任务，再决定界面里放什么。** 早期图把查询和保存做成可拖动的工具卡；讨论后左侧改为资料选择，内部 Tool 留在后端。学员要选的是本轮数据，不是 Agent 的工具权限。
2. **生成图帮助讨论，实际页面仍要审核。** 颜色、布局和消息宽度经历过否决与调整；获批图片只确定设计方向。真实页面还要检查长文本、焦点、侧栏、窄屏、失败态和草稿保护。
3. **把界面动作写成双端 Spec。** 前端负责选择、展示与确认入口；后端负责资料身份、权限、Tool 规则和真实写入。分阶段开发前写正常、失败与回归预期，不能看结果后再改预期。
4. **让业务事实回到当前资料和 Tool。** 模型有回复不等于工单查询完成；上传与选中也不等于本轮使用。记录数、时效和来源要能回到本轮 Tool 输入及结构化结果核对。
5. **报告保存是独立的副作用。** Agent 只准备草稿；用户确认后，后端复核并写文件。取消、重复请求、刷新和重启分别检查，页面显示“已保存”仍需文件回读。

## 出现过的偏差，下一次怎样避免

前端阶段曾出现额外查询条件被忽略、键盘焦点丢失、旧成功提示覆盖新状态等问题。它们促使我们把“规范”落实为会失败的具体用例，并明确状态由谁写、何时失效。后续真实模型链也记录过连接错误和人工重试，因此“后来成功”不能抹去第一次失败，更不能证明课堂单次演示稳定。

下一次开工，先写用户任务、资料样本和一个能暴露错误实现的反例；再定需求、设计、双端 Spec 与阶段验收。接入 Agent 时先守住资料、权限和 Tool 的确定性边界；调优回复放在业务结果正确之后。交接时分开报告已验证、失败与未验证项。
