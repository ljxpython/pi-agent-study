# 一个小型 Agent 应用，如何从界面想法走到可验收的前端

这份案例面向准备使用 Agent 开发第一个小项目的学员。读完后，你应能把一个界面想法拆成用户任务、交互规则和可验证结果，解释为什么添加或删除一个功能，并为自己的项目提前设计反例。

本文第 1—8 节重建截至 2026-09-21 的**前端演示阶段**，其中“当前演示”“待接后端”均指当时，不是今天的运行状态。项目随后接通 Pi SDK、HTTP/SSE、模型、报告保存与恢复；本机验收范围和限制见[项目入口](../00-项目入口.md)。第 9 节记录 2026-09-23 的新一轮视觉讨论：设计与 Spec 已确认，改版代码仍待实施。本文是按关键决策重建的教学案例，不是完整聊天逐字稿。

## 1. 最初想做的项目，实际有两个目标

业务目标：让用户把工单资料变成有来源、能追问、可确认的处理结果与交接报告。

教学目标：通过一个足够小的项目，让学员理解需求、界面、数据契约、Agent 会话、工具、文件交付和状态恢复怎样衔接。

这两个目标相关，却不能相互代替。业务用户不需要先理解 SDK 才能查工单；学员看到漂亮页面，也不等于学会了接入 SDK。原课程交接方案已有最小链资产；后续明确建立独立项目，先做前端演示，再分阶段接后端。这个阶段调整不意味着旧后端样本的运行结果可以继承到新项目。

第一版应先回答一个具体问题：一个第一次打开页面的人，不靠讲师解释，能不能知道这里做什么、如何开始、执行到哪一步、结果是否真的保存了？

## 2. 哪些决定改变了项目

| 起点或反馈 | 最后的选择与原因 | 为此承担的代价或边界 |
|---|---|---|
| 需要看清输入、对话与成果 | 三栏默认展开：左侧资料、中间对话、右侧成果。Agent先解释，右侧再承接可核对结果 | 三栏是本案例选择，小屏改用抽屉；并非所有应用都适用 |
| 参考图里的石青与浅金很好看，整页实现却不满意 | 回到已经认可的浅底、白卡、蓝色交互 | 配色需要在真实页面面积和文字密度下判断；不能只看色卡 |
| 用户要使用自己的模型 | 保留设置入口，区分配置表单、连通测试、实际调用 | 前端保存交互不代表已连通；密钥与配置读取留真实后端处理 |
| 最初把查询、保存做成可拖拽工具卡 | 左栏只保留资料，查询和保存由应用内置 | 用户不必为了完成任务先装配内部工具；界面选择也不授予执行权限 |
| 工单查询还不足以展示教学所需的资源能力 | 顶部增加能力库：模板可查看、编辑、恢复默认，Skill只读；通过正斜杠发现命令 | 这是教学目标明确后的新增范围；不扩成插件市场、脚本编辑器或通用工作流平台 |
| 用户只记得 query 的一部分 | 补全支持前缀、中间片段、大小写及中文匹配；选择只填入，发送才执行 | 搜索候选可以宽松，执行校验仍严格；已有草稿需保护 |
| 两侧收起后仍留大片空白 | 收为窄条，把宽度交还中间；分隔线可拖动并设置边界 | “可拖动”需要最小宽度、恢复行为和小屏策略，不能承诺无限自由 |
| 资料不能只有上传入口 | 增加当前资料选择、来源过滤和文件名搜索 | 筛选只改变列表，不能偷偷更换分析来源；内置示例让用户不上传也能试用 |
| 没有资料时似乎不能开始 | 增加职责、访问范围、能力边界的快捷问题；介绍无需资料，真实查询才检查资料 | 当前只演示有限问法；真实自然语言回答待接模型，不能用大量固定回复冒充 Agent |
| 是否要显示工具、扩展和子 Agent 过程 | 建议面向业务展示短步骤，技术详情按需展开，错误和待确认必须可见 | 仍是后端待确认方案；没有真实事件就不展示虚假的执行成功 |

这里既有可避免的遗漏，也有合理探索。无意义的工具拖拽、折叠不释放空间、无资料入口不清楚，可以在第一次任务演练中发现。能力库和关键词补全则来自进一步明确的教学诉求，不能全部归咎于“最初需求没写好”。

## 3. 最重要的一次转变：不要把内部结构直接搬到界面

“SDK里有工具，所以界面要有工具卡片”跳过了用户为什么要操作它这一步。

先区分四种对象：

| 对象 | 用户真正要做的事 | 本项目放在哪里 |
|---|---|---|
| 资料 | 查看、选择、上传，确定本次分析来源 | 左侧资料栏 |
| 提示词模板 | 看懂任务说明、修改内容、复用到提问 | 能力库和命令补全 |
| Skill | 了解用途及边界，选择适合的任务入口 | 能力库只读详情与命令入口 |
| 内部工具 | 为任务执行查询或保存；通常不需要用户手动装配 | 后端内置；必要时通过执行状态解释 |

检验方法是问：如果去掉这个控件，用户还能否完成同一个任务？如果能，而且没有失去必要选择或理解，这个控件可能只是暴露了实现细节。

这不意味着所有工具都应隐藏。面向开发者的调试台，或需要用户配置工具集合的产品，可能需要工具界面。本项目的业务工作台没有这个任务。

## 4. 一张静态图，还缺少哪些设计

默认页面只展示系统的一瞬间。实现前至少走过当前流程中会发生的状态：首次打开、无资料、已选择、输入中、运行中、错误、停止、等待确认和完成。

以“报告”为例，中间回答说明结论与下一步，右侧承接草稿；用户预览后确认，才能进入保存。取消、超时、停止都不能被当成同意。演示保存只写浏览器内存，也必须说明刷新会丢失。

以“收起侧栏”为例，验收不能只检查内容隐藏。还要看侧栏是否真正变窄、中间是否变宽、重新展开是否恢复，以及窄屏是否仍能使用。

以“填入模板”为例，空输入框可直接填入，有草稿时则需选择替换或保留；选择菜单项不应立即发送。列表搜索也不应改变已经选中的业务资料。

因此，设计稿负责展示方向，交互合同负责描述变化，真实浏览器负责验证实际行为。三者共同覆盖的问题不同。

## 5. 极简代码，为什么还要保留保护逻辑

本项目没有为了教学规模引入线程池、消息队列或分布式锁，但仍需要限制文件大小、校验数据、取消任务、保护草稿和防止重复确认。

单线程也有异步时序：旧任务的回调可能晚于新操作到达。修整过程中曾出现旧成功提示覆盖资料移除提示、输入更新重建无关节点导致焦点丢失，以及只提取关键词而忽略否定条件的问题。

改进方向是减少重复状态、只更新必要节点、拒绝未支持的业务条件；不是删除所有检查，也不是搭一个更大的状态框架。必要保护让行为更容易解释，冗余同步才增加理解成本。

例如“查询平台团队open工单，不要urgent”不能偷偷变成“查询urgent工单”。当前有限演示选择明确拒绝不支持表达；以后真实模型可以澄清，但仍不能丢掉用户的条件。

## 6. 下一次项目，先完成这六步

| 步骤 | 先产出什么 | 如何检查 |
|---|---|---|
| 1. 定用户与结果 | 一句用户任务、一个成功结果；教学目标另外写 | 能解释业务价值；不只列技术名词 |
| 2. 给对象分工 | 数据、配置、任务入口、内部能力、成果分别归位 | 每个可见控件都对应用户的一次必要判断或操作 |
| 3. 走入口与退出 | 无资料怎样开始；何时必须补资料；完成、取消、失败怎样结束 | 不把某个业务动作的前提误当所有操作的前提 |
| 4. 验证交互再细化视觉 | 在同一页面检验配色、长文字、窄屏、折叠、草稿和确认 | 图中看得懂，浏览器里也能连续完成任务 |
| 5. 分批实现 | 每批只改一个明确行为及必要上下文，先同步合同 | 正常用例成功，关键反例能阻止错误结果 |
| 6. 绑定当前证据 | 记录实际版本、真实与演示依赖、结果及未完成项 | 旧审核不覆盖新代码；界面保存不等于磁盘保存 |

这六步可放在一份简短任务说明里，不必机械创建六个文档。其目的不是消灭所有需求变化，而是更早暴露会影响产品方向的遗漏。

## 7. 给自己的 Agent 一段更具体的输入

```text
先阅读当前需求和设计，不改变已确认技术栈。
这次请实现一个小型业务助手的最短用户闭环。
先列出：目标用户、核心任务、必要输入、最终结果和非目标。
把可见内容分成资料、用户可管理的任务资源、内部执行能力与成果；
每个控件说明用户为什么需要操作它，内部工具不要默认做成拖拽卡片。
逐项说明无资料、已有草稿、运行中、失败、取消和完成时的行为；
只分析项目实际存在的状态，不创建额外流程平台。
用一个成功样例和一个能暴露错误实现的反例冻结本批行为，再做最小实现。
验收时检查来源、草稿、焦点及窄屏，说明演示边界与真实依赖缺口。
新反馈先判断是缺陷、遗漏、新增范围还是未验证假设，再决定改动。
```

实际使用时，仍需附上你的业务需求、数据样本和项目约束。这段提示不能自动补出正确业务规则。

## 8. 学员练习：把经验迁移到另一个小项目

选择一个“会议资料问答助手”，先不写代码，完成三个小任务：

1. 画出无资料和已选资料两种状态。问“你能做什么”与“这场会议有哪些决定”分别需要什么输入？反馈标准：前者可以说明，后者缺证据时不能编造。
2. 假设内部有读取、摘要、保存三个工具。决定哪些需要独立界面入口，并写理由。反馈标准：理由来自用户任务，不是因为 SDK 暴露了这个工具；保存的副作用和确认清楚。
3. 写三个反例：草稿被模板覆盖、筛选列表改变了分析来源、报告保存失败却显示成功。反馈标准：指出预期结果、观察位置和负责模块，而不是只写“增加测试”。

交给同学或 Agent 只读你的说明尝试执行。记录哪里还需要补问，修正对应合同，再进入代码。没有做过独立接手，就不要声称文档已经能让任何人顺利复现。

从当时前端演示进入真实后端阶段，仍须分别验证模型连接、资源生效、工具权限、报告落盘和重启恢复；此前的前端经验不能代替这些证据。项目现已取得相应本机验收，具体范围与未测项以当前验收记录为准。

## 9. 阶段 08：从“好像没底”到可测的界面合同

用户在真实页面上指出两个感受：工作台上下缺少完整边界；用户和 Agent 的消息都是居中长方形，身份与阅读方向不清楚。我们先分别生成“整体外框”和“左右交替对话”两张候选图。第二张并未一次通过：用户发现上方消息带比下方输入框宽，于是先加宽并对齐输入框；宽度获认可后，再补助手 Pi 标识和输入区提示条；最后把对话方案与外框合成一张基准图。[阶段 08 图文记录](../02-资料与输入/决策过程图集/08-工作台边框与对话布局/00-阶段记录.md)保留修改前截图、五张生成图及每一步反馈。

这次迭代最有用的转折，是把“看着对齐”改成可检查的条件：消息行与输入框量外边框坐标，用户消息靠右、助手靠左；长文本、侧栏拖动、窄屏和滚动条出现时仍要成立。图里画出的连接状态和工单内容不能作为业务真相。实现前先冻结[前端 Spec v1.8 的阶段快照](../03-方案与设计/frontend-spec-v1.8-阶段08实施前快照.md)，再由[现行 Spec](../03-方案与设计/frontend-spec.md)承担开发合同；图片批准只完成设计 Gate，真正的新版浏览器验收还没有发生。

练习：仅凭修改前图和最终合成图，为自己的界面写三条可观察的验收条件，再补一个反例。若写成“更美观”“更像产品”，请继续问：在什么视口、什么消息长度、什么滚动状态下，量哪里才算通过？对照 AC25—AC30B 检查答案是否可交给另一位开发者执行。
