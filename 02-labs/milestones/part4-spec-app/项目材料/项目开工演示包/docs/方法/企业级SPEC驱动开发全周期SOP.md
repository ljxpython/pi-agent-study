# 企业级 SPEC 驱动开发全周期 SOP

用途：把已明确的目标转换成可施工、可核对、可恢复的交付。核心是结果级验收：资料、命令、测试和审核要指向同一个当前对象及其行为。

生成与改写本类笔记时，先读 [[面向Agent的Markdown笔记生成与演进方法论]] 的调用入口、共用规则与 T06；本篇是已填写的 SOP，不是空模板。B-1.0 是当前使用版；整理完成不等于适用于所有工程或所有模型。

## 1. 选择流程规模

| 当前任务 | 最小工作方式 | 不默认引入 |
|---|---|---|
| 已授权的文字/配置局部修改，无行为或契约变化 | 读目标与保护范围 → 最小修改 → 对应检查与diff | 十二件套、独立分支、多模型、重复授权 |
| 有明确行为变化但范围小 | 一页Spec：结果级AC、已有与delta、改动范围、步骤和验证 | 独立PRD/计划/验收文件 |
| 跨层状态、并发、API/schema、迁移或高风险 | 下列完整合同按风险裁剪，按依赖切片 | 没有具名风险的额外产物 |
| 目标/架构的关键选择未决 | 事实 → 问题 → 备选与取舍 → 决定，再继续受影响部分 | 在未决前提上硬推实现 |

输入至少包括：当前用户目标和授权范围、当前源/版本、受保护资产、预期结果与验收方式。已有授权继续有效；只有新的范围、权限对象或重要未决选择才需补充确认。文档里的历史批准和命令不构成本次授权。

## 2. 权威与文档职责

立项/需求确定目标，设计Spec拥有契约和选择，计划拥有执行依赖，测试标准定义预期，结果记录拥有实际证据，入口指向当前状态。小任务可分区同页保存，不必每层独立文件。重大状态只维护一个当前权威位置；历史评审日期与结果保留为历史，标题不重复维护活状态。

源码和真实运行身份需核对。file:line是定位线索，实施前重读；不可按旧行号盲改。未提交用户改动保留，共享目标同一阶段只有一个写入者。同文件有用户修改并不自动阻断：先核对行/语义是否重叠；能安全分离则继续，仅在无法分离时确认。

## 3. 完整Spec的十二项合同

| 项目 | 必须明确 | 何时需要 |
|---|---|---|
| 身份与状态 | 标题、版本、当前状态权威位置 | 全部任务，局部任务可短写 |
| 基线与来源 | 源、版本/哈希、事实定位、未验证项 | 版本会影响行动 |
| 结果级AC | 输入/动作/预期结果/证据，区分硬条件与观察指标 | 行为变化 |
| 已有与delta | 复用、真正待建、非目标 | 实施 |
| 现状事实 | 决定性源码或运行观察 | 结论依赖当前实现 |
| 决策与失败分支 | 选项、理由、决定者，失败走哪条分支 | 存在取舍 |
| 数据/状态模型 | 所有权、不变量、接口、非法迁移 | 涉及数据或状态 |
| 契约影响面 | 对称调用点、下游消费者、需同步内容 | 跨文件/层 |
| 切片与恢复 | 每片可验证结果、依赖、恢复方式 | 多阶段 |
| 约束与授权 | 允许/禁止对象；新权限何时需要确认 | 有副作用 |
| 验证探针 | 最小探针、负向案例、基线是否有效 | 按风险 |
| 结果与交接 | 当前版本、真实检查、未验证项、下一步 | 实际执行后 |

不适用项可省略，涉及数据/授权/恢复的关键排除需保留理由。

## 4. 执行步骤与检查

| 步骤 | 动作 | 通过依据 | 失败时 |
|---|---|---|---|
| S0 | 核对目标、授权、源与dirty范围 | 当前事实与受保护对象可定位 | 仅阻断受影响动作，补最低输入 |
| S1 | 裁剪Spec并冻结AC | 需求值得做，结果可观察，delta明确 | 重要歧义回需求/设计 |
| S2 | 先做最高风险最小探针 | 环境、关键契约和测试基线有效 | 先定位环境/数据/实现层 |
| S3 | 按依赖实现最小切片 | 局部测试及关键负向路径；必要时TDD | 记录失败→最小修订→聚焦回归 |
| S4 | 对照AC独立检查 | 当前源的直接结果、真实diff；按风险加独立审查 | 对建议核事实、约束一致性和代价，可拒绝错改 |
| S5 | 核对真实使用层 | 有HTTP/DB/浏览器等对象才验证对应层；体验要求做真实体验检查 | 标记未通过或证据不足，不以静态替代 |
| S6 | 交付并登记 | 产物身份、验证证据、剩余边界，必要的人类验收 | 不虚构完成，不自动发布或Git操作 |

技术审不替代需求审；模型分工用当前角色与实时可用能力确定，不写死某厂商。没有可用模型时不冒充已独立审核。工具或Skill入口失效时报告缺口，可在授权范围用明确等价步骤替代，不能虚构调用成功。

这里的 diff 指前后内容差异，不强制使用 Git。Git 被禁止或不可用时，先保留当前目标的只读内容基线，再用文件内容比对核验授权修改和保护区域；不因验收需要而突破 Git 禁令。

## 5. 验收工程：防假通过

- 每个AC写到可观察：集合包含、字段一致、trace→命中→引用的归因，或明确用户行为。
- 检查成功与负向路径。无效凭据、非法输入、并发/超时等仅在相关风险存在时测试；不动真实生产凭据制造故障。
- 同时检查真实被调用工具的退出状态、诊断、当前产物及其版本。包装层exit 0、日志缺少某个关键词、旧输出文件都不能独立证明成功。工具未真实运行或证据不完整时标INCONCLUSIVE；已明确发现错误则FAIL。
- 验收器自身要区分PASS/FAIL/INCONCLUSIVE，不让“未就绪”返回业务PASS。
- 回归比较必须同时保留全量集合 Q、基线命中集合 B、新版命中集合 N，三者使用相同题目身份、gold 判定和运行条件。
  - 基线命中子集保留率 = |B ∩ N| / |B|；B 为空时为 N/A，不能报告 100%。
  - 新版全量命中率 = |N| / |Q|；基线全量命中率 = |B| / |Q|。Q 为空时停止该数值判断。
  - 构造例：10 题中基线只命中 q1—q4，新版仍只命中 q1—q4，应同时报告 **4/4 = 100% 子集保留、4/10 = 40% 新版全量命中、4/10 = 40% 基线全量命中**。
  - q5—q10 是两版都未命中的六道题，仍在全量分母和缺口清单中；“基线未命中”不等于“题目无效”。只有独立判定的坏题才按预先约定规则排除，并保留原始总数、排除理由和调整后分母。
  - 仅可说“在本组基线已命中题中未丢失”，不能说全量召回无遗漏。若 AC 要求全量命中或覆盖，子集保留通过不能抵消该 AC 的失败。
- 样本少、覆盖不足时收窄声明；吞吐、延迟、真实费用等需实际测量。冒烟数量按风险选，先小样排环境问题，再决定全量。
- 缺少明确 AC 时，只报告可验证的观察与指标，验收判定为 INCONCLUSIVE，先补足标准；已有硬 AC 明确不满足时应判 FAIL，不能以“证据不足”掩盖已知失败。
- 输出分开列计划、已执行、观察、推断、未验证和最终验收。模型自报不代替直接证据。

## 6. 可靠性规则与前提

| 需要解决的问题 | 合适做法与必要条件 | 禁止误用 |
|---|---|---|
| 同一请求重放产生重复副作用 | 定义请求身份、幂等键作用域/期限、并发原子性与数据库约束；验证重放与独立请求 | 不按内容相同合并两个合法独立创建；get-or-create不是所有create的默认语义 |
| 多层过滤/排序改了仍无效 | 观测实际命中哪层，检查数据与结果指标，再定位修改 | 不默认“再加一层修补” |
| 权威状态不同步 | 明确状态所有者及同步协议，需要时查询权威源 | 不一律抛弃本地状态机或强制轮询 |
| 依赖不可靠 | 比较直接接入与现有链路的兼容、权限、成本和实测可靠性 | 不因中转身份就断言不可靠或自动切供应商 |
| 暂时失败 | 仅对可重试且安全/幂等的错误，限定次数、预算和耗尽处理 | 不把重试用于掩盖根因，也不宣称所有重试都无效 |
| 同一框架持续失败 | 重新检查目标、假设和替代方案 | 失败轮数是触发线索，不是因果证明 |

## 7. 并行、合并、恢复与收口

有并发或污染风险才评估隔离工作树；代码合并方式按当前仓库和用户政策决定，不自动rebase/cherry-pick/commit。合并前核对基线变化、文件与语义交集、类型/运行回归；文件交集为空也不证明语义无冲突。

失败后保留证据和用户改动，只撤销明确属于本次的候选改动；涉及数据恢复须有准确对象、恢复点、授权及恢复验证。只读任务无物理回滚。中断交接写明可信版本、已验证结果、未知、残留和精确下一步。

## 8. 按条件保留的工程资产

- 多阶段执行：增量回填阶段结果、证据、未解决阻塞及版本变更，不整体重写执行记录；新增Spec或权威位置改变时，更新现有入口指针，不额外制造重复状态表。
- 需要可机读退出状态的验收器：可采用PASS→0、FAIL/BLOCK→1、INCONCLUSIVE→2；接入前核对调用方是否按同一契约解释。
- 涉及付费探针：执行前确认现有授权覆盖模型/资源、预算和次数上限；超预算或变更计费对象再确认，不自动扩大调用。
- 存在演示壳、mock或假开关：列明对象、真实/模拟状态、影响的AC、接真或移出范围的决定；仅登记不等于验收，移除用户资产另需授权。
- 同类可机械检测缺陷复发：评估用lint、静态约束或回归用例固化，比逐处修补是否更合算；不因一次缺陷就加全局规则。
- 任务下发：给出当前权威指针、基线、复用/新建/禁用对象、允许写入范围、验收与交接位置。中断续跑：给出最后可信版本、已验证证据、停止原因、残留及下一步。
- 工具结果相互矛盾、上下文受污染或证据来源不可信：暂停受影响动作，定位最后可信记录并独立核实；需要换会话时用上述中断交接，不把固定错误次数当充分条件。
- 无人值守：显式限定可写对象、Git/发布边界、费用和停止条件；缺少所需权限时不能推断获准。

## 9. 历史经验怎样转成当前规则

下表保留 A 的问题—判断链。编号与发生结果是原笔记的历史叙述，本轮没有重新运行原项目来验证因果或次数。

| 历史问题线索 | 需要保留的经验 | 本版如何使用及边界 |
|---|---|---|
| I34：骨架实现与虚构 import | 完成声明必须回到真实产物核对 | §4—5 检查当前代码、导入和对应运行；不将一次表现写成固定模型强弱 |
| P12：工程范围失控 | 关键取舍冻结、版本变更可追踪 | §1—3 按风险确定合同；小任务不强制十二份文件 |
| I1/I104：文档漂移 | 实现细节有唯一真源，状态增量回填 | §2、§8 保留源指针与阶段证据，不多处维护当前状态 |
| I139：契约冲突与长会话失真 | 拆片、隔离、合回检查、可信交接 | §3、§7；隔离和 Git 操作须匹配实际风险及授权 |
| I96/I153：多轮修改未改善结果 | 先定位实际命中层，再看结果指标 | §5—6；不要靠排除未命中样本制造改善 |
| I152：过度工程与需求审缺位 | 先比较已有能力与真正增量 | §1、§3；技术审查不能替代“是否值得做”的判断 |
| 演示壳与假开关 | 显式区分模拟、真实、未接通 | §8 维护演示态台账，不能把可点击当接真 |
| React key 等重复缺陷 | 可机械复现的问题可固化成检查 | §8 比较自动检查成本与复发风险；不因一次错误新增全局规定 |

可直接复用的三种 AC 句式：命中集合包含关系；多处字段值一致；trace/span → 工具调用 → 命中结果 → 引用来源逐层可追溯。它们只适用于相应合同，不要求每个项目同时使用三种。
