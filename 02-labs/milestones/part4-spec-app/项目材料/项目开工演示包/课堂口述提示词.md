# 课堂口述提示词｜从开工目录到需求、设计

这份话术根据现存 002 项目文档 **反推** ，不是当年的聊天记录或真实原提示词。第二章演示前三段：读取并追问、确认后生成需求、审过需求再生成总体设计。后面的资料登记和双端 Spec 供后续阶段使用。所有生成都在开工包的 **复制品** 里进行；发放的原始包仍不含需求、设计和 Spec 正文。

## 备课依据：成品告诉我们要给 Agent 什么

以下路径相对于原始 `002-Pi工单问答助手/` 项目。复制的开工包没有这些原件，讲师需把本轮决定口述给 Agent。

| 原项目成品 | 可反推的输入 | 不能反推成第一轮已确认的事 |
| --- | --- | --- |
| `01-目标与需求/需求范围.md` | 本机工单交接、业务用户与学员两类目标、选资料查询与追问、带来源的结果、人工确认报告、阶段范围 | 能力库、时效、恢复等是后来多轮补充 |
| `02-资料与输入/来源.md`、教学 JSON、视觉基线和决策过程图集 | 样本与图片来源；默认资料和 U01 的不同预期；采纳四张浅色图的视觉方向，否决工具卡拖拽 | 图中文字、记录、连接和保存状态不是运行事实 |
| `03-方案与设计/frontend-spec.md` | 三栏工作台、资料选择与发送分开、草稿确认、错误与窄屏状态须可检查 | 当前 v1.8 的全部增量与通过记录 |
| `03-方案与设计/backend-spec.md` | SDK 会话、当前资料绑定、确定性工具、报告批准及文件恢复由应用负责 | 精确接口、十分钟确认期等后期合同 |

整段课堂口述围绕一句话： **我选中一份资料后，助手怎样只用这份资料回答，结果怎样核对；要保存报告时，谁批准、谁写文件？** “平台 open 工单”中的 open 指“尚未关闭”。

## 第一段：先读材料，只追问

> 我们从这个新项目目录开始。请先读根目录的 AGENTS.md、00-项目入口.md、docs/方法/工程规范.md，再读 docs/方法/大型项目防返工开工范式.md 的第一、二、六节。用自己的话说出本轮适用的三条约束、还没确定的事，以及这个课堂小项目怎样裁剪平台项目的开工材料。我想做一个本机使用的 Pi 工单问答助手，让人选工单资料、提问、看来源，需要时形成报告。现在先别写代码，也别生成需求或设计。最多问我五个会改变第一版范围、数据和工具权限、报告交付或验收的问题，并说明为什么重要。

**讲师检查：** Agent 是否读了入口、约定和本轮适用的方法章节，是否问到使用者、资料来源、能否改工单、是否允许外部模型，以及怎样验收查询和保存。曾对只有工程规范的原始开工包做过一次只读试跑：Agent 读了当时的三份文件并提出五问；加入两份新方法后的提示词尚未试跑，不能把旧结果当作本版验证。

## 讲师口述回答示例：把第一轮决定说出来

这是课堂可采用的 **示范确认口径** ，不是历史逐字原话。某项尚未决定就说“待确认”，不要照念成已批准需求。

> 使用者先按本机单人来做。业务用户要整理待交接的工单；学员借这个项目看清网页、Pi SDK 和业务工具怎样连接，这两个目标分开验收。资料先用教学 JSON，不接企业工单系统，不使用真实客户数据。用户能选默认资料或上传资料，问“查询平台团队尚未关闭的工单”；结果要有记录、数量、来源，还可以追问。默认样本查出三条，U01 练习样本查出一条，这只是验证资料切换的样本预期，不是业务常数。原工单只读；资料无效时要报错，不能把上轮结果说成本轮成功。报告先给我看草稿，我确认后应用才保存；取消不能生成最终文件。第一版不做多人协作、公网发布、自动改工单或任意格式导入。真实模型和 Pi SDK 是完整产品方向；这一轮只写文档，不调用外部模型，也不把“准备接入”写成“已经接通”。联网与数据发送边界若仍有疑问，先标待确认。

**讲师停一下：** 再问“还有哪个问题会实质改变第一版范围？”回答并明确确认后，才进入第二段。后期才决定的能力库、时效规则、确认期限和重启恢复细节，先不要倒灌进初始回答。

## 第二段：确认后生成需求文档

> 刚才我口述的第一版范围和限制，现在确认作为需求输入。请只生成 docs/需求/需求.md，并在 00-项目入口.md 加上现行链接。按“谁用、在什么场景、选哪份资料、做什么、看到什么、失败怎么办”写清用户任务。把业务交接目标与学员学习目标分开，把完整产品目标与本阶段准备做的事分开。写出选默认资料查询、切换到 U01 再问同一句、无效资料、取消报告的可检查情形，结果要说明记录、数量、来源和是否产生文件。把已确认决定、教学样本数字、你的建议及待确认问题分别标明。不要预设具体接口、十分钟确认期限或后期能力库范围；不要写设计、Spec 或代码。完成后指出关键需求来自我的哪句回答。

**讲师检查：** “选中资料”与“工具实际查这份资料”是否分别可验；三条与一条是否仅为样本预期；草稿生成是否没有写成文件已保存。出现未经确认的决定，先修需求。

## 第三段：需求审过后生成总体设计

> 我已经检查并确认现行需求。请重新读 AGENTS.md、00-项目入口.md、工程规范和 docs/需求/需求.md，并根据防返工范式第二节检查意图、契约、反馈和变更方面的关键风险。现在只生成 docs/设计/架构决定.md，并更新入口链接。沿“选资料 → 发问题 → 读取本轮资料 → 返回记录与来源 → 追问 → 报告草稿 → 用户确认或取消”说明责任链：前端管选择、输入和展示；后端管请求资料身份与版本、Pi SDK 会话、受控工单工具，以及确认后的文件保存。Pi SDK 管 Agent 会话、模型交互和工具调用；应用管业务筛选、来源、权限、批准、文件和恢复。每个设计决定标出对应需求、失败行为与待验证点。图片中的工具卡或“模型已连接”字样只能作为讨论素材，不能当成已批准功能或运行证据。未决定的接口、时效、期限和恢复细节标待确认；不要生成前后端 Spec 或代码。

**讲师检查：** 页面显示选中 U01 后，设计是否还要求后端绑定 U01，让工具返回 U01 来源；模型准备草稿后，是否仍要等人确认，由应用写文件。这里的“总体设计”是课堂补出的中间文档；真实 002 项目保留的是持续修订的前端、后端 Spec，不能说当年就有同名 `架构决定.md`。

## 后续话术 A：把实际图片与样本登记成输入

只有在讲师 **实际提供** 图片和 JSON 样本后使用。它可以作为第三段设计前的补充输入；只凭“有四张图”不能让 Agent 编造图中内容。

> 我现在提供四张工作台参考图、两份答案不同的教学工单资料，以及我对图的反馈。请先核对实际文件，再新建 docs/输入/ 并生成来源.md，登记名称、类型、来源和可核对的样本预期，并在项目入口加链接。四张浅色图只采纳浅底、白卡、蓝色交互和三栏方向；左栏拖入查询工具卡这一步我否决，左栏改为资料入口，工具由应用受控调用。把“图片支持的视觉方向”“我明确确认的交互决定”“图片无法证明的运行状态”分开写。若文件没交给你，就列缺失项，别编造图中内容、记录或哈希；不要改需求、设计、Spec 或代码。

原始开工包没有这些图片和样本；未准备好文件时，可只口述取舍，让 Agent 在设计里注明“待核对原图/数据”。默认三条与 U01 一条的预期应在运行前写下，并核对样本内容。

## 后续话术 B：从已确认设计生成前端 Spec

第二章不执行。先确认需求、设计和视觉输入；“先做前端演示”是阶段范围，不是完整产品已接通。

> 我确认前端先做可操作的本机工作台，并确认浅色三栏、左栏只放资料、查询工具不拖拽。请读现行需求、设计、输入来源、真实图片，以及企业级 SPEC 驱动开发全周期 SOP 第一、三至五节，按风险确定这次前端演示适用的合同项；只生成 docs/规格/frontend-spec.md，并在项目入口加现行链接。这阶段先做“前端演示”，不接真实后端；完整产品的真实模型与文件保存保留为后续目标，不要混写。按用户动作给出可验收条件：选资料与发送问题分开；默认和 U01 查询结果与来源可区分；无效资料不冒充本轮成功；报告先预览，取消不显示已保存；窄屏和折叠保留主要任务。图片文字、日期、工单数与“模型已连接”不能直接当成实现事实。写清已有、待做、不做、需后端配合的接口及每项在浏览器怎样验证。若真实模型或磁盘保存未接入，明确标为演示，不写成已通过。

后期若又确认模板/Skill 能力库、命令补全或边框与对话布局，只针对该反馈增量修订对应验收条件；不要把现行 `frontend-spec.md` 的全部历史增量塞进最初一版。

**贴近真实项目后期版本的追加口述：** “我现在确认能力库只展示本应用的模板、Skills、Tools、Extensions、Packages；只有模板可编辑，其他只读。命令选择只填入输入框，不立即执行；编辑草稿不能被切换操作静默覆盖。之后我又确认工作台要有完整外框，用户消息靠右、助手靠左，消息与输入框共用同一内容带。请分别把这些新增决定写成受影响的前端验收条件，注明参考图约束视觉而非运行状态；保留旧版本的历史状态，不把这次修订写成已经通过浏览器验收。”

## 后续话术 C：从前端动作生成后端 Spec

第二章不执行。业务规则、模型配置、报告格式和恢复目标尚未确认时，先留待决项；实际 SDK 能力要按实施时锁定版本核对。

> 请重读现行需求、总体设计、前端 Spec 和企业级 SPEC 驱动开发全周期 SOP 第一、三至五节，先指出哪些页面动作需要后端持有真实状态、哪些合同项因跨层状态和文件保存风险必须写清，再只生成 docs/规格/backend-spec.md，并在项目入口加现行链接。按一次请求讲清资料身份与版本、Pi SDK 会话、受控查询工具、确定性时效计算、记录和来源；按报告动作讲清草稿、用户确认或取消、文件保存与回读。把 SDK 会话历史与应用保存的资料选择、请求状态、报告批准和文件分开。给出默认与 U01 切换、非法资料、工具失败、取消、重复确认、刷新或重启后的正反验收；模型回答、工具结果、页面状态和磁盘文件分别用什么证据。工具不能修改原工单，也不能自行批准保存。未确认的时效口径、确认期限、接口字段、存储方式和模型供应商标待确认或待验证，不照抄已有工程的后期参数。只写 Spec，不安装依赖、不调用真实模型、不写应用代码；完成后列出需要我确认的关键取舍。

**贴近真实项目后期版本的追加口述：** “我现在补充并确认业务口径：只有 open 工单参与待处理超时判断，严格超过阈值才算超时；缺少分析时间或时限仍可普通查询，但不能猜测超时。用户可在对话中明确补充规则，只作用于本次分析；只有用户明确说‘按现在分析’才取本条消息的接收时刻。报告交付为 Markdown 预览和下载，草稿经人确认后保存；独立输入的 API Key 只留后端内存。待确认动作十分钟有效，过期不自动保存；来源和依据未变时可由用户重新申请确认。请把这些决定逐条增量写入后端 Spec，给出边界样本、失败与恢复条件；接口细节仍要在实现前核对，不能把 Spec 写成已运行通过。”

这段是后期追加决定，课堂只有在讲师明确说出并批准后才给 Agent；绝不接在第一段初始需求后直接让它生成最终 v0.15。

## 课堂停点

第二章最迟停在“复制品中需求和总体设计已写出、讲师能指出决定来源及未知项”；发放的原始包中 `docs/需求/`、`docs/设计/`、`docs/规格/` 仍为空。资料登记与双端 Spec 是后续续接话术。现存 002 项目文档能帮助倒推 **提示词应给哪些信息和检查点** ，不能证明当年的提示词原文、精确生成顺序，或最终版本一轮就完成。
