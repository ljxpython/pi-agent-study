# 从一个需求点到双端 Spec：工单助手的制作过程

这份材料用于第二章。它把真实项目的关键决定压缩成可复用的练习路径；**不是完整聊天记录，也不是现行工程 Spec 的副本**。图片是设计讨论输入，运行结果要另行验证。

## 先准备一个可持续读取的项目目录

如果是你自己从零开始的新项目，先创建独立的项目文件夹。课上可直接复制[项目开工演示包](./06-项目开工演示包/README.md)到自己的工作区，再在复制品根目录启动 Agent；其中的[课堂口述提示词](./06-项目开工演示包/课堂口述提示词.md)按“只读追问→确认后写需求→需求通过后写设计”分三段。下面是这个新项目示例的结构，不是随课学员版应用的现有目录；学员版应用从 `Pi工单问答助手-学员版/README.md` 进入，项目内 `frontend/`、`backend/` 和 `samples/` 同级。

```text
my-ticket-assistant/
├─ AGENTS.md                         简短项目约定
├─ 00-项目入口.md                    当前目标、状态和文档导航
└─ docs/
   ├─ 方法/工程规范.md               开工前放入的完整方法文档
   ├─ 需求/需求.md                   追问确认后生成
   ├─ 设计/架构决定.md               分工确认后生成
   └─ 规格/
      ├─ frontend-spec.md           前端阶段实施前生成
      └─ backend-spec.md            后端阶段实施前生成
```

在自己选定的工作区父目录执行 `mkdir -p my-ticket-assistant/docs/方法`，然后放入 `AGENTS.md`、`00-项目入口.md` 和工程规范。后面几份文件按讨论结果逐步建立，不预填未经用户确认的需求。工程规范可使用本课提供的[0.3 原文快照](./参考文档/Vibe-Coding工程方法论与Agent开发规范-v0.3.md)。

`AGENTS.md` 可先写成下面这样，实际项目的用户决定和文件范围以后再补：

```md
# 本项目开发约定

- 开工先读 `00-项目入口.md` 与 `docs/方法/工程规范.md`，复述适用规则和未知项。
- 需求未确认前先追问，不把假设写成既定需求。
- 进入开发阶段前，读取入口指向的现行需求、设计和该阶段 Spec。
- 改动后交出实际差异、正常与失败样本的检查结果，以及仍未验证项。
```

`00-项目入口.md` 初始只写项目目标草案、当前状态和“工程规范在 `docs/方法/工程规范.md`”；需求、设计与 Spec 确认后再添现行文件链接。完整方法留在 `docs/方法/`，入口只维护链接，避免三处复制全文。

把文件夹交给开发 Agent 时，明确要求它先读项目入口、项目约定和工程规范，复述适用规则与未知项，再开始需求讨论。进入下一阶段或文档有更新时，重新让它读取现行文件，并核对规则是否进了 Spec、改动和验证结果。文件一直可读，不表示 Agent 自动知道最新版或自动遵守。

## 再给开发 Agent 什么任务信息

项目开始前先交代：谁使用、要完成什么动作、输入资料是什么、最后交付什么、第一版不做什么。再给一份工程方法 Markdown，要求 Agent 只提取适用于当前项目的规则，并写明落到哪条需求、哪处代码和哪种验证。本项目登记的工程输入是《Vibe-Coding 工程方法论与 Agent 开发规范》0.3；其中最有用的三条是：**需求能用正常与失败场景反驳、契约先规定输入输出与权限、验证结果必须绑定版本和实际输入**。把文档发给 Agent，不等于它已遵守这些规则。

开工对话可以直接使用下面的输入。它是**课堂重演模板**，不是本项目当时的原话，也不能据此认定曾调用某个追问 Skill。

> 我想做一个本机使用的工单问答助手。请先读取项目根目录的 `AGENTS.md`、`00-项目入口.md` 和 `docs/方法/工程规范.md`，复述本轮适用规则与未知项，暂时不要写代码。先梳理用户、任务、输入、成果和非目标；再追问最多五个会改变架构或验收的问题。每个问题说明：不同回答会改变什么。得到回答后，给出需求草案、前后端职责和待确认的架构决定；未经我确认，不要把假设写成既定需求。文档确认后写入 `docs/需求/` 与 `docs/设计/`，并更新项目入口的链接。

若用追问 Skill，可让它执行同一张问题卡：**问题 → 为什么影响设计 → 可选回答 → 用户决定 → 改动的需求或 Spec**。本项目保存的材料足以证明多轮反馈改变了设计，尚不足以指认早期具体 Skill 的名称与版本。应用里的工单分诊 `ticket-triage` 是运行时 Skill，和开发阶段的追问用途不同。

Agent 的第一轮产物应分开检查：需求文档说清用户、任务、第一版范围和可反驳的正反场景；设计文档说清前后端职责、资料与请求流转、允许的 Tool 和报告写入权。由你确认架构取舍及待验证假设，再交给 Agent 逐阶段补前后端 Spec。本项目由需求范围与前后端 Spec 承载这些内容，不声称另有已冻结的独立架构设计书。

## 本项目怎样逐段落地

<div align="center">

| 阶段 | 交给 Agent 的输入 | 人来确认什么 | 留下的产物与检查 |
|---|---|---|---|
| 目录与开工输入 | 项目入口、`AGENTS.md`、工程规范 | 哪些约束适用于本项目，哪些仍待决定 | Agent 复述规则与未知项；后续阶段重新读取现行文件 |
| 需求与架构 | 任务、资料、成果、非目标、工程规则 | 本机单用户、前端展示与后端受控执行的边界 | `docs/需求/` 与 `docs/设计/` 中的决定、正反场景；入口更新链接 |
| 先定前端 | 界面需求和逐轮生成的视觉图 | 哪张采纳、哪张否决，用户少做了什么 | 设计基准、`docs/规格/frontend-spec.md`、实现后的浏览器核对 |
| 从界面补后端 | 已确认的选择资料、提问、报告确认等动作 | 哪些状态和权限不能只由页面决定 | 资料绑定、受控 Tool、`docs/规格/backend-spec.md` 中的草稿与保存合同 |
| 分阶段开发 | 前后端各自的现行 Spec、写入范围、正常与失败样本 | Agent 的改动与结果是否符合先前决定 | 源码差异、测试、实际页面和未验证项 |
| 反馈再迭代 | 真实页面、失败记录、用户新反馈 | 改的是视觉、交互还是业务规则 | 更新受影响的 Spec，再验证受影响链 |

</div>

这是一条**讲解顺序，不是虚构的严格时间线**。真实项目在前端代码前已有前端 Spec，后端实现前已有后端 Spec；两端后来有交叠和多轮增量，不是“所有代码写完才写 Spec”。

## 从一个页面动作写双端 Spec

选“切到上传资料再查询”作为例子。前端 Spec 约定：用户能看到已选资料，选择与发送是两个动作；界面不能把上一轮记录显示为本轮成功。后端 Spec 约定：请求绑定资料身份与版本，业务 Tool 只读本轮资料；版本不匹配或资料无效要明确失败。两端一起验收：上传样本只得该样本记录，切回默认资料恢复默认记录和来源。

报告按钮再补一条：前端显示待确认草稿；后端持有草稿身份并控制保存，取消不写文件，批准后单次写入。界面能提出后端问题，**权限、异常与重启后的有效性仍需另行确认**。

自己的项目按以下空白卡填写，然后再让 Agent 写对应阶段的 Spec：

```text
用户动作：
可见的正常结果：
失败或取消时应发生什么：
前端要显示／保留的状态：
后端要校验的身份、权限或数据版本：
Agent 可以调用的工具及禁止的动作：
前端 Spec 条件：
后端 Spec 条件：
先写下的正常样本与失败样本：
这阶段允许改的文件／要保留的行为：
实际运行入口、结果与未验证项：
```

给 Agent 执行时，先让它指出现行 Spec 与源码位置，再限定本次改动和停止条件；改完检查差异和正反样本。图片、Spec 审核、测试通过、浏览器操作和真实模型结果分别记录，不能互相代替。

材料来源：项目需求范围、前后端现行 Spec、前端决策图集阶段一至四、前端阶段复盘、工程方法论 0.3。以上只保留教学所需决定；完整现行 Spec 以教师最终冻结的项目版本为准。
