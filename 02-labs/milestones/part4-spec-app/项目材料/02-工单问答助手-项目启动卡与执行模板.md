版本：1.2（2026-09-23案例状态校正）。用途：把准备工作变成可以填写、讨论和交给开发Agent的输入。

当前权威：[002项目入口](../../../../../../04-项目设计制作/002-Pi工单问答助手/00-项目入口.md)。

先阅读[项目启动与交付SOP](./01-小型Agent应用-项目启动与交付SOP.md)。第1节是本案例的设计和截至 2026-09-23 的工程状态摘要；第2节列出学员自己运行时仍须确认的条件；第6—8节是可复制模板。项目实际验收见工程记录，本文不把历史结果当成你本机已通过。

## 0. 课前起点：写出一条可检查的需求

阅读本卡第1节和第4节，以及 SOP 的第1、8、10节。先不用安装项目或调用模型。请写下：“选择只有 U01 的上传资料后，查询平台团队 open 工单”这一动作的**预期结果、失败结果、需要查看的证据**。参考判断：正确结果只包含 U01；如果仍返回默认资料的 T01/T04/T06，表示选择或请求绑定没有得到证明。此时只是纸面预期，不能填写成你的运行结果。

课堂上把这句话补成需求→Spec 条件→验收条件，再用分发工程或隔离练习副本验证；若尚未拿到代码包，仍可完成课前判断，不必猜测本机模型配置。

## 3. 课堂复现脚本（项目有本机历史证据，学员仍须实测）

| 顺序 | 用户动作 | 预期可见结果 | 证据 |
|---|---|---|---|
| 1 | 打开尚未配置的应用 | 可进入设置，明确不能发送的原因 | 页面状态 |
| 2 | 配置自己的接入，分别测试问答与工具，再保存应用 | 明确两个测试结果和实际生效模型 | 脱敏请求结果与模型身份 |
| 3 | 点击默认资料名称，再选择资料 | 可读详情；本轮选择准确 | 选择状态与后端快照 |
| 4 | 询问“查询平台团队open工单，列出ID和统计” | 基线一致时返回T01/T04/T06，3条 | 工具参数、记录、来源 |
| 5 | 补充“只看urgent” | 返回T01，1条 | 新请求与实际结果 |
| 6 | 请生成处理建议报告（不需添加工具） | 先有可读草稿，明确等待确认；没有已保存状态 | 草稿、来源及确认动作 |
| 7 | 先取消；重新生成草稿后确认 | 取消无新文件；确认只新增一份匹配文件 | 前后文件清单与回读内容 |
| 8 | 上传本文件U01样例并选择，查询平台open | 只得到U01，来源指向上传资料 | 数据集ID/版本和结果 |
| 9 | 切回默认资料再查询 | 恢复基线结果；旧报告仍标原来源 | 当前资料与报告来源 |
| 10 | 分别刷新页面、停止并重新启动后端 | 原会话、选择、已保存报告可定位；旧待确认动作失效 | 两类恢复分别记录 |

无资料可问职责、权限边界和操作方法，不强制上传；M1 阶段演示与当前真实问答的证据分别判断。

普通查询先在对话中给出结论，再更新右侧成果；模型总结失败时明确说明并保留可核对的真实记录。报告草稿必须在确认前可见，不能等待最终回复而阻塞批准。已收起的右栏只提示新成果，不自动展开。

## 4. 独立上传样例与负例

以下是构造的教学样例，可保存为 `upload-one-ticket.json`，不是已运行结果：

```json
{
  "now": "2026-09-20T12:00:00Z",
  "policy": {"urgentHours": 4, "normalHours": 24},
  "tickets": [
    {
      "id": "U01",
      "title": "上传验证工单",
      "team": "平台",
      "priority": "urgent",
      "status": "open",
      "createdAt": "2026-09-20T00:00:00Z"
    }
  ]
}
```

查询平台open的预期：ID为U01，count=1，urgent=1，normal=0；来源与所选上传资料一致。时间与policy字段用于保持样例结构；本课查询不按当前时间过滤，也不计算超时规则。

从这份样例另存副本制作负例，不覆盖有效样本：

| 负例 | 制作方式 | 预期 |
|---|---|---|
| 非法JSON | 删除一个必要右括号 | 明确解析失败，不添加可选资料 |
| 必填缺失 | 删除ticket的id | 结构校验失败 |
| 重复ID | 复制记录且保持同一个id | 重复ID被拒绝 |
| 非法枚举 | 将status改为paused | 校验失败，不自动改为open |
| 错误类型 | 将tickets改为字符串 | 类型错误，不返回成功空结果 |
| 超限 | 构造超过需求约定上限的副本 | 明确拒绝；不使用未声明的服务器默认限制判分 |
| 同名重传 | 用同名文件再次上传有效内容 | 新资料身份，不覆盖旧资料或改写旧报告来源 |

边界测试分别覆盖“恰好上限”和“超过上限”；大小按需求约定的文件字节计算，不能与传输时JSON转义后的长度混淆。

## 5. 报告样例：先检查内容，再决定格式

以下示例基于U01查询，供检查阅读体验，不是程序已生成的报告：

```text
平台团队未处理工单摘要

资料：upload-one-ticket.json
资料身份与版本：由后端填入本次查询绑定的真实值
筛选：team=平台，status=open
结果：共1条；urgent=1，normal=0
工单：U01 上传验证工单

处理建议：先核实工单描述和影响，再安排处理。
说明：建议由模型生成，供人工判断，不表示已经完成处理。

当前状态：等待确认，尚未保存
```

确认前核对：记录、数量、筛选条件、资料版本是否来自真实查询；正文是否可读；用户能否知道尚未保存。保存后核对同一内容，并显示实际文件标识。未知事实不由模型补造。
